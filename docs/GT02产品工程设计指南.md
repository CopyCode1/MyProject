# GT02 Zephyr 产品工程设计指南

> 文档状态：初版架构基线  
> 适用工程：GT02 nRF52840 + Zephyr 重新实现项目  
> 维护原则：当产品边界、硬件方案或关键架构决策变化时同步更新本文档

## 1. 文档目的

本项目不是把旧工程中的 FreeRTOS API 逐项替换成 Zephyr API，而是以旧产品的可观察行为为参考，从零建立一个可演进、可验证、可量产的产品软件工程。

本文档服务于三个目标：

1. 指导开发者理解一个嵌入式产品从需求到量产的完整过程。
2. 约束 GT02 新工程的模块边界、依赖方向和技术选择。
3. 为后续代码评审、问题定位、硬件换型和功能扩展提供共同依据。

旧工程是以下内容的参考来源：

- 产品已经具备的功能；
- 协议格式、业务规则和服务器兼容行为；
- 外设初始化顺序及硬件限制；
- 正常、异常和边界场景下的可观察表现；
- 可复用的纯算法、协议编解码和经过验证的芯片寄存器操作。

旧工程不是以下内容的默认依据：

- 新工程的目录结构；
- 模块依赖关系；
- 线程和定时器的组织方式；
- 全局变量和全局函数的使用方式；
- nRF5 SDK、SoftDevice或FreeRTOS接口的延续。

## 2. 产品工程的核心思想

### 2.1 从问题和验收标准开始

任何功能在编码前都应能够回答：

- 用户或设备要解决什么问题？
- 输入、输出和触发条件是什么？
- 什么结果代表功能完成？
- 超时、断电、通信失败和外设故障时应该怎样表现？
- 功耗、时延、Flash、RAM和可靠性限制是什么？

如果无法回答这些问题，代码通常只是在实现一种猜测。

### 2.2 隔离变化，而不是抽象一切

新架构要重点隔离未来可能变化的部分：

- PCB和引脚连接；
- SoC型号；
- IMU、UWB、GNSS、4G和Flash芯片；
- 通信通道；
- 产品业务策略；
- 云端协议版本；
- Bootloader和升级策略。

不需要为了形式上的“解耦”包装每一个 Zephyr 函数。驱动和平台适配层可以自然使用 Zephyr；真正需要保持独立的是产品业务规则、协议逻辑以及稳定的服务边界。

各层只公开当前调用者实际需要的能力，内部步骤、等待、错误检查和资源管理尽量封装在实现内。先保持接口收敛，后续有明确业务需求再扩展，不为假设中的功能提前增加入口。当前4G硬件适配以初始化、上电、下电、读、写五个入口为起点。

### 2.3 依赖只能指向更稳定的抽象

推荐依赖方向：

```text
产品业务 / Domain
        ↓
应用服务 / Services
        ↓
设备与平台接口 / Ports
        ↓
Zephyr适配与芯片驱动 / Adapters & Drivers
        ↓
Devicetree、Kconfig、Zephyr内核与驱动框架
```

上层可以依赖下层提供的抽象接口，下层不能反向调用具体业务模块。事件通知应通过回调、消息或事件接口完成，而不是让驱动包含业务头文件。

### 2.4 用纵向功能切片持续交付

不要先写完所有驱动，再写所有服务，最后一次性集成。优先完成能够被观察和验证的纵向功能链，例如：

```text
GNSS UART接收
  → NMEA解析
  → 定位服务
  → 上报策略
  → JT808/XRP编码
  → 4G发送
  → 服务器响应
```

每个切片都应包含必要的接口、实现、日志、错误处理和测试。这样可以尽早发现架构边界是否合理。

## 3. “解耦成功”的判定标准

解耦不以目录数量或接口数量衡量，而以变化影响范围衡量。

| 变化 | 预期主要修改范围 |
|---|---|
| PCB引脚调整 | board DTS、pinctrl或overlay |
| 更换同类IMU | IMU驱动、compatible和少量配置 |
| 更换4G模组 | modem适配器及AT命令实现 |
| 更换nRF52840为其他Zephyr SoC | board、DTS、底层平台适配 |
| 修改定位融合策略 | domain或location service |
| 修改服务器协议 | protocol库和对应业务适配 |
| 增加BLE OTA通道 | BLE传输适配，不修改镜像写入核心 |

出现以下情况通常意味着边界失效：

- 业务代码出现物理引脚号、UART实例号或寄存器地址；
- 业务代码包含具体传感器或4G模组的头文件；
- 更换PCB需要修改多个业务模块；
- 驱动直接决定产品工作模式；
- 多个模块可随意写同一个全局状态；
- BLE、UART和4G各自实现一套Flash升级规则。

## 4. 从0到1的产品生命周期

### 4.1 阶段A：产品定义

目标是确定“做什么”和“做到什么程度”，而不是讨论函数怎么写。

必须形成：

- 功能清单；
- 主要使用场景；
- 产品状态和状态转换；
- 外部接口与协议清单；
- 非功能需求；
- 明确不做的内容；
- 每项需求的验收方法。

GT02功能域初始清单：

- BLE连接、配置、数据交互和升级传输；
- 4G注册、联网、Socket管理和业务上报；
- GNSS定位和时间获取；
- UWB测距或定位；
- IMU运动、静止和姿态信息；
- LED、按键、马达、显示或音频交互；
- 电池、电源路径、休眠和唤醒；
- 参数、设备身份、离线数据和故障信息存储；
- JT808、XRP、NTRIP或其他产品协议；
- Bootloader、固件校验、升级与回滚；
- 工厂测试、烧录和设备初始化。

非功能需求至少考虑：

- 冷启动和联网时间；
- 定位首次成功时间和更新频率；
- 正常、待机和深度休眠功耗；
- 通信丢包、弱网和长时间离线行为；
- Flash和RAM预算；
- 数据保存周期和Flash擦写寿命；
- 看门狗恢复时间；
- OTA失败和断电恢复；
- 运行温度、电压和外设异常；
- 固件签名、设备密钥和调试口策略。

阶段出口：每个计划实现的功能都有可验证的完成标准。

### 4.2 阶段B：系统设计

目标是决定系统如何分解以及各部分如何协作。

应输出：

- 系统上下文图；
- 硬件资源表；
- 软件模块图；
- 接口与事件清单；
- 线程和执行上下文设计；
- 数据所有权和持久化设计；
- Flash、RAM和栈预算；
- 电源状态和唤醒源设计；
- 风险清单与验证计划。

阶段出口：主要模块职责单一，依赖方向明确，高风险方案已有验证办法。

### 4.3 阶段C：工程与板级基础

目标是建立可重复构建、烧录、调试和验证的最小系统。

建议顺序：

1. 构建和版本信息；
2. RTT或UART日志；
3. 自定义board和Devicetree；
4. LED与按键；
5. 系统时钟、复位原因和看门狗；
6. ADC与电源控制；
7. I2C、SPI和UART总线连通；
8. 外部Flash；
9. 基础休眠与唤醒。

阶段出口：新板能够稳定启动，每项硬件资源有独立的最小验证方法。

### 4.4 阶段D：平台服务

目标是为产品功能提供统一的公共能力：

- 系统事件和消息传递；
- 单调时间、UTC时间和时间同步；
- Settings/NVS配置存储；
- 设备身份和版本信息；
- 日志、指标、复位原因和故障记录；
- 看门狗与健康监控；
- 电源状态协调；
- 固件镜像写入与升级状态管理。

阶段出口：产品功能不需要重复实现这些基础机制。

### 4.5 阶段E：产品功能切片

按风险和产品价值逐个完成端到端功能。推荐初始顺序：

1. 按键触发、LED反馈和电源状态；
2. 配置存取和设备信息；
3. GNSS定位与本地日志；
4. 4G入网和最小数据上报；
5. 完整定位上报链路；
6. IMU运动状态；
7. BLE配置和诊断；
8. UWB功能；
9. 低功耗策略；
10. MCUboot与多通道OTA。

顺序可以根据硬件交付和业务优先级调整，但每个切片都必须可单独验证。

### 4.6 阶段F：产品化与量产

功能运行不等于产品可出货。量产前至少完成：

- 长时间运行和内存稳定性测试；
- 弱网、断网和服务器异常测试；
- 反复上下电、低电压和棕断测试；
- OTA下载中断、写入中断和回滚测试；
- 工作模式和极限场景功耗测量；
- 工厂测试流程；
- 序列号、证书和密钥写入；
- 发布版本、变更记录和可追溯构建；
- SWD、读保护和生产固件安全策略。

## 5. 软件分层和职责

### 5.1 Domain：产品业务层

负责稳定的产品规则，例如：

- 产品主状态机；
- 定位和上报策略；
- 报警判定；
- 运动状态对产品行为的影响；
- 离线数据补传规则。

约束：

- 不包含Zephyr驱动头文件；
- 不访问Devicetree；
- 不知道GPIO、UART、I2C、SPI实例；
- 不依赖具体芯片或模组类型；
- 尽可能通过普通C输入、输出和接口进行测试。

### 5.2 Services：应用服务层

负责协调多个能力形成业务用例，例如：

- location_service：统一GNSS、UWB及可能的融合结果；
- network_service：管理联网、连接和收发；
- ble_service：提供业务级连接和命令事件；
- storage_service：提供参数和记录语义；
- ota_service：统一下载、校验、写入和升级状态；
- power_service：协调系统工作模式和设备电源请求。

服务可以使用Zephyr的线程、工作队列和同步原语，但不应向业务层泄漏底层设备细节。

### 5.3 Ports：稳定接口层

接口描述“上层需要什么能力”，而不是“芯片有哪些函数”。例如，modem接口可以表达：

- 上电和下电；
- 查询注册状态；
- 建立和关闭连接；
- 发送数据；
- 上报异步状态和接收数据。

接口不应直接暴露某个模组的AT命令字符串或内部状态结构。

### 5.4 Adapters与Drivers：实现层

负责将稳定接口映射到具体实现：

- Zephyr GPIO、UART、I2C、SPI、Flash和Sensor API；
- 具体IMU、UWB、GNSS和4G模组；
- 必要时使用nrfx或厂商库，但必须限制在适配层内部；
- 将硬件事件转换成服务可理解的事件。

### 5.5 Board：板级描述

板级内容包括：

- SoC和存储容量；
- 引脚复用；
- 总线实例；
- 外设地址、片选和中断；
- aliases和chosen节点；
- Flash分区；
- 板级默认配置。

禁止在普通C业务文件中用`#ifdef PRODUCT_GT02NEW`选择引脚。

## 6. Zephyr配置职责划分

| 机制 | 应负责的内容 | 不应负责的内容 |
|---|---|---|
| Devicetree | 实际存在的硬件、连接关系、地址、中断、分区 | 用户策略和运行时业务状态 |
| Kconfig | 编译期功能选择、缓冲区大小、栈大小和驱动能力 | PCB物理连接 |
| CMake | 源文件和组件的构建组织 | 产品运行逻辑 |
| prj.conf | 某个应用构建所需的Zephyr能力 | 直接描述引脚 |
| overlay | 板级变体或构建变体的硬件差异 | 大量业务条件编译 |

`build/`目录是生成结果。不得手工修改其中的Kconfig、头文件、Devicetree或构建产物来实现功能。

## 8. 并发和事件模型

### 8.1 不延续全局20 ms轮询

旧工程集中调用所有模块`Poll`的方式容易产生：

- 无意义唤醒和额外功耗；
- 最坏执行时间难以计算；
- 某个模块阻塞导致整个系统延迟；
- 模块之间隐含执行顺序；
- 故障定位困难。

新工程优先使用事件驱动：

- GPIO中断只采集最小信息，实际处理提交到工作队列；
- UART异步接收负责搬运数据，解析在适当上下文完成；
- 周期任务使用`k_work_delayable`；
- 精确定时或轻量通知使用`k_timer`，回调内不做阻塞工作；
- 连续、阻塞或具有独立生命周期的功能使用专用`k_thread`；
- 跨模块消息使用`k_msgq`、`k_fifo`或明确的事件接口。

### 8.2 创建线程的判断标准

满足以下一项时才优先考虑专用线程：

- 必须调用阻塞API；
- 有独立且长期存在的控制循环；
- 必须隔离执行时延或栈；
- 具有清晰的所有权和生命周期。

不要为每个小模块创建线程。每个线程都应记录职责、优先级、栈预算、阻塞点和看门狗策略。

### 8.3 状态所有权

一份可变状态应有一个明确所有者。其他模块通过命令、查询接口或事件访问，不允许多个线程无规则修改同一全局结构。

## 9. 外设和驱动设计

### 9.1 通用原则

- 优先使用Zephyr已有驱动和标准子系统；
- Devicetree描述实例，不在代码中硬编码实例；
- 初始化时使用`device_is_ready()`验证依赖；
- 明确同步调用与异步回调的执行上下文；
- 接口返回统一、可判断的错误；
- 驱动不得静默无限重试；
- 对复位、掉电和重新初始化行为作出定义。

### 9.2 GNSS与4G

至少拆分四个层次：

```text
UART传输
  ↓
数据帧或AT解析
  ↓
具体模组状态机
  ↓
GNSS/Modem稳定接口
```

AT命令解析不能与云端协议、定位策略或产品状态机写在同一个模块中。

### 9.3 IMU

能满足需求时使用Zephyr Sensor API。若芯片特殊功能超出标准API，可增加产品扩展接口，但标准采样和属性设置仍优先遵循Zephyr模型。

### 9.4 UWB

DW1000等UWB驱动可能包含大量厂商代码。可以复用经过验证的寄存器和算法核心，但应建立独立端口层封装：

- SPI收发；
- CS控制；
- IRQ；
- RESET和WAKE；
- 时间和延时；
- 临界区或同步操作。

厂商代码不得直接访问产品状态或其他业务模块。

## 10. 产品状态机设计

GT02主状态机应描述产品行为，而不是硬件初始化步骤。初始可考虑：

- BOOT：启动和恢复原因分析；
- SELF_TEST：关键硬件自检；
- ACTIVE：完整业务运行；
- POSITIONING：集中定位过程；
- IDLE：低活动等待；
- SLEEP：可唤醒低功耗；
- SHUTDOWN：受控关闭；
- FAULT：受限运行或恢复。

每个状态都应定义：

- 进入条件；
- 进入动作；
- 接受的事件；
- 超时；
- 退出条件；
- 退出动作；
- 故障和降级行为。

状态转换应可记录、可测试，避免通过多个布尔变量隐式表达状态。

## 11. 错误、恢复和可观测性

### 11.1 错误处理

错误至少区分：

- 参数或编程错误；
- 暂时性外部错误，例如弱网；
- 可恢复设备错误，例如总线超时；
- 持久性硬件错误；
- 数据损坏或安全校验失败。

每类错误应明确：立即返回、有限重试、设备复位、功能降级、系统重启或进入故障状态。

### 11.2 重试策略

所有重试必须有：

- 最大次数或最大时间；
- 退避策略；
- 成功后的状态恢复；
- 失败后的升级处理；
- 可观察的日志或计数器。

### 11.3 日志规范

日志用于说明状态变化和故障原因，不用于持续打印无价值信息。建议包含：

- 模块名；
- 关键状态转换；
- 外部错误码和内部映射错误；
- 重试次数；
- 重要请求的关联标识；
- 固件版本、复位原因和启动计数。

禁止输出密钥、完整认证数据或敏感用户数据。

### 11.4 看门狗

看门狗不是在任意循环中定时喂狗。应由健康监控确认关键执行单元仍在正常推进，再统一喂狗。系统卡住时应允许看门狗真正触发，并在下次启动保存和上报复位原因。

## 12. 数据与存储

存储内容应分类：

- 出厂数据：设备身份、硬件版本、校准值；
- 用户配置：工作模式、服务器地址、功能开关；
- 运行状态：升级状态、启动计数、最近错误；
- 业务记录：离线定位、事件和补传数据；
- 临时缓存：断电后不要求保留。

每类数据需定义：

- 所有者；
- 版本号和升级方式；
- 默认值；
- 写入频率；
- 原子性要求；
- 损坏后的恢复方式；
- 是否包含敏感内容。

小型配置优先使用Settings/NVS。大量顺序记录应评估独立日志结构或文件系统，不要把高频数据当普通配置反复写入。

## 13. 电源管理

低功耗不是最后加入的单个开关，而是跨模块设计。

必须明确：

- 产品电源状态；
- 每个状态允许工作的设备；
- 唤醒源；
- 外设下电和恢复顺序；
- 未完成通信或Flash写入时能否休眠；
- 定位、上报和低电量之间的策略；
- 调试配置与发布配置的功耗差异。

各驱动负责自身挂起和恢复，power service负责协调产品级策略。业务模块不得随意直接切断其他模块使用中的电源。

## 14. Bootloader、Flash和OTA

### 14.1 Flash布局应提前规划

典型逻辑区域：

```text
MCUboot
Primary Application Slot
Secondary Upgrade Slot
Settings / NVS
Factory Data
Crash / Diagnostic Data
```

最终地址和大小必须根据内部Flash、外部Flash、镜像大小、升级策略和回滚要求计算，不能直接照抄示意图。

### 14.2 传输与升级核心分离

BLE、USART和4G只是固件数据来源：

```text
BLE / USART / 4G transport
             ↓
统一下载与分片接口
             ↓
镜像写入、哈希和签名校验
             ↓
MCUboot pending / confirm / revert
```

传输层不决定Flash地址和镜像切换规则。升级核心不需要知道数据来自BLE还是4G。

### 14.3 OTA验收场景

至少验证：

- 正常升级；
- 重复包和丢包；
- 下载中断后继续或重来；
- 擦除、写入和验证阶段断电；
- 镜像损坏或签名错误；
- 新固件启动失败自动回滚；
- 新固件确认成功；
- 版本策略和必要时的防回滚。

## 15. 测试策略

### 15.1 测试层次

- 纯单元测试：协议、算法、状态转换和数据校验；
- 组件测试：服务与伪设备接口组合；
- 板上驱动测试：每个外设的最小功能和异常行为；
- 集成测试：完整纵向功能链；
- 系统测试：真实设备、网络、服务器和功耗；
- 生产测试：焊接、总线、传感器、射频及身份写入。

### 15.2 可测试性要求

- 业务逻辑使用显式输入，不直接读取硬件或全局时间；
- 时间、设备和网络等外部依赖可以替换为测试实现；
- 状态机转换有确定输出；
- 协议解析覆盖正常、截断、异常长度和错误校验；
- 错误注入能够验证重试、降级和恢复。

### 15.3 功能完成定义

一个功能只有同时满足以下条件才算完成：

- 需求和验收标准明确；
- 边界和依赖符合架构；
- 正常路径可运行；
- 主要异常和超时已处理；
- 日志足以定位故障；
- 相关测试通过；
- Flash、RAM、栈和功耗影响已评估；
- 文档和配置同步更新。

## 16. 旧工程重新实现策略

对每个旧模块执行以下分析，而不是直接复制：

1. 列出外部可观察功能；
2. 找出输入、输出、状态和时序；
3. 标记纯逻辑与硬件/RTOS耦合部分；
4. 为新工程定义稳定接口；
5. 先为纯逻辑建立测试向量；
6. 在Zephyr中实现适配器；
7. 使用相同输入对比新旧输出；
8. 达到行为一致后再替换旧功能。

可以优先复用：

- 经过验证的纯算法；
- 协议结构和编解码规则；
- 测试数据；
- 芯片厂商提供且确有必要的底层核心。

需要重新设计：

- 主函数和初始化流程；
- FreeRTOS任务、队列、定时器和全局Poll；
- SoftDevice BLE事件模型；
- 板级宏和直接寄存器调用；
- 模块间全局函数调用；
- Bootloader和OTA状态管理。

## 18. 代码评审检查表

### 架构

- 修改是否位于正确层次？
- 是否出现反向依赖？
- 是否把板级或芯片细节泄漏到业务层？
- 新接口是否表达能力，而不是复制底层芯片API？
- 是否引入了不必要的抽象？

### 并发

- 状态所有者是否唯一？
- 回调或中断上下文中是否存在阻塞操作？
- 队列满、超时和线程退出如何处理？
- 锁顺序和共享数据是否明确？
- 栈大小是否有依据？

### 可靠性

- 错误是否被检查和传播？
- 重试是否有限并带退避？
- 设备失效是否会拖垮无关功能？
- 断电或复位是否会损坏持久数据？
- 日志能否说明失败发生在哪个状态？

### Zephyr

- 硬件描述是否放在Devicetree？
- 编译期功能是否使用Kconfig？
- 是否误改`build/`生成文件？
- 是否优先使用已有Zephyr子系统？
- 设备使用前是否验证ready状态？

### 验证

- 是否覆盖正常和主要异常路径？
- 是否提供可复现的测试步骤？
- 是否评估资源和功耗影响？
- 文档是否需要同步更新？

## 19. 常见反模式

- 在`main.c`中完成所有初始化和业务处理；
- 一个“公共头文件”包含所有模块和全局变量；
- 使用大量`#ifdef PRODUCT_xxx`表达板型；
- 将芯片驱动返回值直接扩散到所有业务代码；
- 每个模块创建一个线程，却没有明确执行模型；
- 在中断或定时器回调中执行阻塞通信；
- 遇到失败无限重试；
- 通过延时碰运气解决时序问题；
- OTA传输层直接写死Flash地址；
- 只验证功能成功路径；
- 手工修改`build/Kconfig`等生成文件；
- 把旧工程目录整体复制进新工程后再逐步“整理”。
