## 1. 第一性原理：模组不是函数库，而是串口另一端的计算机

### 1.1 最简单的物理模型

MCU和4G模组是两个独立运行的系统。它们通过UART收发字节：

```text
MCU发送方向：程序 → UART TX ─────────→ 模组RX → 模组处理
MCU接收方向：程序 ← UART RX ←───────── 模组TX ← 模组产生数据
```

MCU执行一个发送函数，不是在直接调用模组内部函数，而是在把请求写到通信线上。
对方可能尚未启动、正在忙、发生故障，也可能已经处理完成但回复还没到。

UART可以同时收发，不等于能任意同时执行多条AT事务。前者是物理通信能力，后者取决于命令协议能否区分回复归属。

例如发送：

```text
AT\r\n
```

在线上对应四个字节：

```text
41 54 0D 0A
 A  T  CR LF
```

模组回复的字节也不是“一个OK对象”，而可能是：

```text
0D 0A 4F 4B 0D 0A
```

这里的`\r`、`\n`是表示控制字节的写法，不是线上真的有反斜杠和字母r、n。

### 1.2 一次接收回调不是一条消息

同一段回复可能被驱动分成：

```text
情况A：[\r\nOK\r\n]
情况B：[\r] [\nO] [K\r] [\n]
情况C：先收到另一条URC，再和OK一起进入同一个缓存批次
```

所以必须区分：

```text
UART读取批次 ≠ AT文本行 ≠ TCP接收片段 ≠ 产品业务报文
```

驱动什么时候回调受硬件、缓冲和调度影响，不能拿它当产品协议边界。

### 1.3 设计取舍D01：怎样操作UART？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 一直轮询接收 | 原理直观，适合最初验证 | 持续轮询会耗CPU；调用者忙时容易来不及接收 |
| 中断接收＋缓存 | 能及时搬运字节，机制较小 | 要处理缓存容量、并发和唤醒 |
| 异步UART API | 适合批量传输和缓冲生命周期管理 | 缓冲归还、停止、错误恢复更复杂，也要核对控制器支持 |

**本工程先保留现有中断RX＋缓存；短AT命令可以继续同步TX。** 有性能测量依据后再考虑异步TX/RX。
UART接口选择见[Zephyr UART官方说明](https://docs.zephyrproject.org/latest/hardware/peripherals/uart.html)。
该说明区分轮询、中断和异步API；本工程当前用的不是异步UART回调接口，不要因为“软件异步”就把两者混为一谈。

升级UART实现不能代替上层事务设计。即使DMA一次收到整块数据，回复归属、二进制边界和超时仍要处理。

## 2. 从字节到文本行：先解决边界，再谈含义

### 2.1 第一版接收器只需要积攒一行

处理方法是：收到普通字符就存起来，收到协议规定的行结束符后，才交给下一步处理。

```text
依次收到：R → D → Y → CR → LF
缓存变化：R   RD  RDY
遇到行尾：产生一条文本行“RDY”，清空本行长度
```

实际协议常有空行和CRLF组合。必须按照当前模组的语法决定结束符如何消费。
纯文本日志中可以不显示空行，但不能因此推导“协议解析器随时都能丢掉CR/LF”；二进制阶段会推翻这个做法。

当前工程曾逐字符打印，是因为每次从UART缓存读到一点就打印一点，不是模组发了很多单字符URC。
后来增加跨批次行缓存，才恢复完整行显示。日志拼行与协议解析是两个目的：前者方便人看，后者决定程序行为。

### 2.2 字节数组不自动是C字符串

假设缓存先装过长文本，后装短文本，只覆盖了前面的字节：

```text
旧内容：Revision: NT26KCNF20NNA-Q02011622
新有效内容：+CPIN: READY
后面仍可能残留：26KCNF20NNA-Q02011622
```

若没有在新内容末尾补NUL，字符串函数可能看到：

```text
+CPIN: READY26KCNF20NNA-Q02011622
```

这正是本工程已遇到的CPIN误判来源。边界不是靠“看起来像字符串”确定的，而是靠有效长度确定的。

当前`response_text()`对四个零参数文本回调做了边界处理：

```c
/* 原理摘录，适用前提见实际函数，不是任意SDK回调的通用公式。 */
data->match_buf[prefix_length + len] = '\0';
```

这里SDK的`len`不含匹配前缀，不能直接写`match_buf[len]`。
换成有参数拆分或DIRECT回调时，长度语义可能不同，必须重新核对调用约定。

### 2.3 设计取舍D02：怎样判断接收内容结束？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 一次UART读取算一条 | 最省代码 | 回调分片或多条合并就出错，不能作为正式协议设计 |
| 一段时间没字节就算结束 | 能临时观察一些设备 | 调度和链路停顿会误切；不能证明完整消息已收到 |
| 根据协议分隔符/长度解析 | 不依赖UART读取批次 | 需要保存解析状态，并定义超长、截断等错误行为 |

**选择协议边界。** 当前纯AT文本用行边界；以后提示符和二进制使用各自规则。
接收空闲超时可以用于发现“收了一半卡住”，不能代替协议边界。

## 3. 只发AT、等待OK：一个事务是怎样出现的

### 3.1 给操作建立起点和终点

先只允许一条命令在途：

```text
IDLE
  │ 准备本次事务并发送AT
  ▼
WAIT_FINAL
  ├─ 收到本次允许的OK ─→ SUCCESS
  ├─ 收到ERROR等结束响应 → FAILURE
  └─ 到截止时间仍未完成 ─→ TIMEOUT
```

“事务”不是凭空增加的架构概念。只要你开始问“我现在等谁、什么时候不再等”，事务就已经存在了。

事务至少需要保存：当前操作、预期回复规则、截止时间、结果以及完成标志。

### 3.2 等待的正确顺序

```text
1. 获得发送权
2. 准备结果槽，清理属于本次事务的通知状态
3. 注册预期响应，标记当前事务处于等待状态
4. 发送命令
5. 等待完成通知或到截止时间
6. 读取结果，撤销规则，结束事务并释放资源
```

不能先发送、过一会儿再准备等待条件：对方可能回复很快，通知已经到达却被你随后清掉。
更不能在接收回调里清理掉刚刚产生的有效结果。

完成通知只是“结果可读了”的信号。结果应先写好、再通知；等待方醒来后读取结果，而不是看到信号就无条件认为成功。

### 3.3 阻塞等待不等于CPU忙等

```text
命令线程：发送 → 等待信号量，暂时不占CPU → 被唤醒 → 读取结果
接收线程：持续处理RX → 识别结果 → 写结果 → 通知命令线程
```

同步接口可以通过内核等待让出CPU。它会阻塞调用它的线程，但不等于整个系统都停住。
如果同一个线程既负责接收又等待接收结果，那才容易形成“等自己来处理”的死锁。

### 3.4 设计取舍D03：怎样等待结果？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 循环检查全局变量 | 容易写出第一版 | 忙等耗电；加sleep会增加延迟；并发与可见性容易含糊 |
| 固定延时后认为成功 | 调试时似乎简单 | 时间到了不等于收到结果；太短误判、太长浪费等待 |
| 结果槽＋内核完成通知＋超时 | 唤醒及时，结果可验证 | 需要明确通知归属、同步和清理顺序 |

**选择第三种。** 当前工程用信号量承担事务完成通知，这是合理起点；有信号量仍不自动解决迟到回复问题，见第13章。

## 4. 从OK增加到“数据行＋OK”：一条查询不只有一个结果

### 4.1 用实际CPIN查询理解

用户已经观察到：

```text
MCU → AT+CPIN?
模组 → +CPIN: READY
模组 → OK
```

`+CPIN: READY`是业务数据，`OK`是这次命令的结束响应。二者职责不同：

```text
数据行到达：把SIM状态保存到本次结果，标记“已见所需字段”
OK到达：本次命令结束，检查数据是否齐全、格式是否合法
最终交付：事务成功＋有效SIM状态
```

如果只收到OK，却没有CPIN数据，不能凭空报告SIM已就绪。
如果收到数据行却迟迟没有最终响应，也不能假定整个交互已正常结束。

### 4.2 还要识别回显

关闭回显前，可能看到：

```text
AT+CPIN?          ← 对方把收到的命令原样回显
+CPIN: READY     ← 查询数据
OK               ← 最终响应
```

回显不是结果，也不是URC。`ATE0`只是减少这种干扰，不能代替解析器区分消息角色。
`OKAY`也不能只因以`OK`开头就算成功；应按该命令允许的结束响应规则判断。

### 4.3 数据坏了，为什么通常仍要收完结束响应？

假设CSQ数据格式非法，但后面马上跟着OK：

```text
旧事务：+CSQ: abc,99 → 回调记录格式错误
旧事务：OK          → 才结束事务
```

如果收到坏数据就立即发下一条，旧事务的OK可能被误认为新事务成功。
所以本工程先记录解析错误，等当前事务结束，再向服务报告错误；真有失步风险时还要进入恢复，而不是继续发命令。

### 4.4 设计取舍D04：什么时候报告查询成功？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 第一个数据行就成功 | 看起来响应快 | 忽略最终ERROR或后续字段，容易留下尾部响应 |
| 看到OK就成功 | 实现短 | 缺数据也会被当成功，无法提供可信状态 |
| 数据校验＋最终响应共同决定 | 结果完整、结束条件明确 | 要保存seen、解析错误和结果副本 |

**选择第三种。** 当前代码里的`query.seen`、`query.error`和最终响应等待，就是这个思路。
例如RSSI的99表示未知，不能改成“正常信号”；错误码也不能把SIM failure猜成未插卡。

## 5. 加入URC：串口从问答机变成事件通道

### 5.1 为什么会有没问过的回复？

模组内部还连接着运营商网络和远端服务器。MCU没有发送命令时，也可能发生启动、掉网、来数据、连接关闭等事情。
模组主动输出的通知通常称为URC，即非请求式结果通知。

当前已经遇到的真实例子是启动时的`RDY`。它不由某次AT查询直接产生，不能拿它替代OK释放事务。

**本章以后，`+PEER_CLOSED`、`+DATA`、`AT+OPEN`、`+OPEN_RESULT`等均为虚构教学协议。**
它们用于解释机制，不是让你向NT26直接发送的指令；实际拼写、字段、分隔符和顺序必须查对应模组手册。

现在考虑下面的交错：

```text
MCU：AT+CSQ
模组：+PEER_CLOSED: 2      ← 连接2被远端关闭
模组：+CSQ: 18,0          ← 当前查询的数据
模组：OK                  ← 当前查询结束
```

不能因为正在等CSQ，就忽略连接关闭；也不能因为收到连接关闭，就把CSQ事务判为失败。
这是两个对象上发生的两件事，可以同时成立。

### 5.2 不要只分“我的回复”和“垃圾”

解析后至少需要区分：

| 类别 | 示例 | 交给谁 |
|---|---|---|
| 当前事务数据 | `+CSQ: 18,0` | 当前事务结果槽 |
| 当前事务结束 | `OK`、允许的错误响应 | 当前事务完成机制 |
| 主动状态事件 | 远端关闭、掉网、模组重启 | 后端转换后通知服务 |
| 先前异步操作的结果 | 某次连接的结果URC | 对应待完成操作，而非随便一个当前AT事务 |
| 回显、空行、未知文本 | 依协议识别 | 忽略已知噪声，未知情况计数/记录/诊断 |

“异步”说的是发生时间不受当前调用控制，不代表它永远和请求无关。
某次TCP连接请求的最终结果也可能以URC形式到达。

### 5.3 同前缀既能是查询回复，也能是URC

本工程的CGREG就能帮助理解：查询回复通常包含模式n和状态stat，主动通知的字段布局可能不同。
不能简单规定“以加号开头就是URC”或“匹配到了前缀就是当前回复”。
应结合当前事务、字段语法、待完成操作及协议模式判断。
相关标准边界见[ETSI TS 127 007的CGREG定义](https://www.etsi.org/deliver/etsi_TS/127000_127099/127007/18.08.00_60/ts_127007v180800p.pdf#page=290)。
CGREG和LTE/EPS的CEREG也不能在服务语义里直接当同一个命令名；后端应提供统一且含义明确的注册结果。

### 5.4 设计取舍D05：怎样处理URC？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 所有收到的内容都追加到当前回复 | 第一版查询容易跑起来 | URC污染查询；没有当前请求时事件无处可去 |
| 全局搜索关键词、修改若干标志 | 初期代码短 | 同前缀和载荷会误匹配，状态归属越来越混乱 |
| 规则＋当前上下文分类，再转换成事件 | 能处理交错、关联与差异 | 需要明确规则优先级、未匹配行为和事件交付 |

**选择第三种。** 注意不是规定所有SDK都先匹配URC或先匹配事务：同前缀要按语法和上下文处理，单一固定优先级不是万能解法。
没有当前事务时收到孤立OK，也不能留着当下一条命令的成功凭据。

## 6. 谁来读串口：先确定一个接收解释者

### 6.1 两个人读同一个串口为什么危险？

假设线程A等待CSQ，线程B等待连接结果，两者都直接读取UART：

```text
串口到达：+CSQ:18,0\r\n+OPEN_RESULT:2,0\r\nOK\r\n
线程A可能拿走：+CSQ:18,
线程B可能拿走：0\r\n+OPEN_RESULT...
```

不是两个人各得到一份，而是把同一条字节流抢着分走了。加很多业务判断也无法把已经丢失的边界可靠补回来。

因此选择：**一个接收入口、一个持续解释字节流的解析者，然后把结果分发给需要的人。**

```text
UART中断
   │ 仅搬运字节
   ▼
原始RX环形缓存
   │ 收到通知后读取当前可用数据
   ▼
接收解析线程
   ├─ 事务响应 → 写本次结果 → 唤醒等待者
   ├─ 状态URC → 规范化事件 → 服务
   └─ 数据载荷 → 对应连接的接收缓冲
```

### 6.2 通知不是数据，也不是计数器

环形缓存保存字节；信号量只表示“可能有事可处理”。多批到达可以合并为一次唤醒。
被唤醒后应处理当前可用内容，不能假设“取到一次信号量就只读一个字节”或“信号量次数等于消息数”。

如果停止接收也会唤醒线程，醒来后还要检查状态/故障，而不是认定一定有新数据。

单生产者、单消费者可以采用适合这种关系的环形缓存使用方式；多生产者/消费者则要另行同步。
`ring_buf`并不自动保护任意并发组合，详见[Zephyr Ring Buffers并发约定](https://docs.zephyrproject.org/latest/kernel/data_structures/ring_buffers.html#concurrency)。
本工程的原始RX路径是UART中断写、接收线程读；不要未经设计再加一个“日志线程”直接抢读它。

### 6.3 回调不能把接收线程堵住

回调的工作应短：校验字段、保存必要结果、投递事件或唤醒等待者。

错误做法：

```text
接收线程发现掉网URC
    → 在URC回调里同步发送重连AT
    → 等待接收线程处理重连回复
    → 当前线程正在等待自己：无法继续解析
```

正确做法是把掉网事件交给服务，由服务安排后续操作。
接收线程不能等待一个已经阻塞等待它的线程来消费队列，否则也会形成循环等待。

### 6.4 设计取舍D06：接收与业务如何组织？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 每个调用者自己读取UART | 单函数看起来独立 | 抢流、丢边界，无法可靠分发URC |
| 中断里直接解析并调用业务 | 表面上延迟低 | 中断时间不可控，不能随意阻塞，耦合扩大 |
| 中断搬运＋单解析者＋短回调 | 接收持续、归属清楚 | 要明确缓存、通知和结果同步 |

**选择第三种。** 不要求每个接收字节都投递消息队列，也不要求每层都有线程。

并发还有一个细节：注册/移除匹配规则、回调结束、结果读取之间需要同步约定。
“发送函数返回”不天然等于“任意解析回调已经完全退出”。
本机SDK的`modem_cmd_handler_update_cmds()`直接更新规则字段，没有在函数内部取得解析锁；
当前代码中关于隐含同步的说明不能当作适用于任意调度或SMP的保证，后续抽取AT核心时应显式审计。
本教程只指出边界，不在文档任务中修改SDK或固件。

## 7. 文本和二进制混在一起：需要切换解析模式

### 7.1 “把所有数据按行切开”什么时候失效？

假设教学模组按以下语法推送数据：

```text
+DATA:2,8\r\n
紧接着8个载荷字节
```

载荷恰好是：

```text
00 0D 0A 4F 4B 3E 41 FF
```

一共8字节，里面包含NUL、CR/LF、字母OK、提示符样子的`>`，还有不可打印字节。
这8字节全部是连接2的数据，不是AT控制信息。

若继续按字符串、换行或关键词解析，就会出现：

- `%s`遇到00提前结束。
- 按CR/LF分行会把载荷切坏。
- 搜到OK就错误完成一条AT事务。
- 搜到`>`就误认为可以开始发送。

**同一个字节的含义，取决于当前协议状态，而不是它长什么样。**

### 7.2 最小解析状态机

```text
TEXT：按控制文本语法处理
  │ 识别完整DATA头，校验连接编号和长度
  ▼
HEADER_EOL：若头部规定CRLF，必须完整消费头部的CRLF
  │ 注意CR与LF可能分批到达
  ▼
RAW_PAYLOAD：无条件按字节消费恰好N字节
  │ 此处不判断NUL、CR/LF、OK、URC或提示符
  ▼
按该模组语法处理载荷后的分隔符，再回TEXT
```

`HEADER_EOL`可以是解析器内部的小状态，不必单独建文件。
关键是头部CR已经到了、LF还没到时，不能把下一批的LF错算为载荷；
进入载荷后，也不能“顺手丢掉所有CR/LF”，因为载荷本身就可能以CR/LF开头。

当前UART批次里可能同时有：头部、半段载荷、剩余载荷和下一条URC。
解析器应循环消费，并在每个状态记录“本次用掉多少字节”，不能处理完第一条就丢掉后半批数据。

示意伪代码：

```text
只要输入还有字节：
    若在RAW_PAYLOAD：
        n = min(输入剩余长度, 当前载荷还缺长度)
        将这n字节交给当前连接，更新剩余长度
        若载荷完成，转到协议规定的下一个状态
    否则：
        按控制语法继续消费头部/行/提示符
    每轮必须消费输入或明确等待更多数据，不能原地无限循环
```

长度为0是否允许、最大长度是多少、尾部是否有CRLF，全部由具体协议定义。
若允许0长度，也应立即完成并推进状态，不能等一个永远不需要的字节。

### 7.3 还有一种不带换行的控制信息：发送提示符

教学流程：

```text
MCU：AT+SEND=2,8\r\n
模组：>                 ← 可能没有CRLF
MCU：发送恰好8字节载荷
模组：SEND OK\r\n
```

只有当前事务处于“等待发送提示符”时，且控制语法允许，才识别这个提示符。
不能在任何位置看到`>`就触发发送，更不能在RAW_PAYLOAD里识别它。
这说明纯“完整行回调”不能覆盖所有AT通信。

### 7.4 设计取舍D07：怎样处理文本与载荷？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 全部当文本，用字符串搜索 | 文本查询很容易上手 | 二进制、提示符、嵌入控制字节会破坏解释 |
| 规定所有数据先转十六进制/转义 | 若对端支持，可统一文本处理 | 字节量增加；协议由模组决定，MCU不能单方面改线上的格式 |
| 控制语法＋长度驱动的载荷模式 | 可保留任意字节、支持分片 | 要处理状态切换、容量、长度错误和失步恢复 |

**选择第三种，具体模式由模组后端描述。** 发送提示符也属于上下文相关的控制语法。
可以复用SDK的直接匹配/定长处理能力，但必须验证消费顺序和缓冲生命周期；不是增加一个配置就自动正确。

本工程当前仍在UART中断拒绝NUL和超长文本，并对QIURC主动停止，因此**当前固件还不能直接接任意TCP二进制载荷**。
后续要把原始传输层变成对字节内容透明，文本长度限制移到合适的解析状态，调试日志也不能把所有载荷按行打印。
UART硬件错误与原始缓存溢出检查仍应保留。

## 8. TCP传的是字节流，不是业务报文

### 8.1 现在有两层不同的边界

UART上的模组头部告诉MCU“这次交付N个TCP数据字节”，但这不等于服务器发的一整条业务消息。
TCP面向应用提供有序字节流，而不是保留每次write/send的消息边界，见[RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)。

例如应用逻辑上发了HELLO和WORLD，接收端可能在不同时间读到：

```text
HELLOWORLD
或 HE / LLOWOR / LD
或 HELLO / WORLD
```

只要字节顺序一致，这些分块都不能仅凭接收调用次数解释成业务消息边界。
网络服务应保持每路字节顺序；产品协议负责从这条字节流重新识别业务报文。

### 8.2 文本数据也要明确协议和编码

“TCP发文本”只是载荷按某种字符编码解释，不会让TCP自动有消息边界。
一个UTF-8汉字的多个字节也可能跨接收批次，不能把每块都当作独立完整字符串解码。
长度字段按字节还是字符计数必须明确；本教程默认以字节计数。

### 8.3 一个最小业务分帧例子

假设我们自己能定义产品协议，选：2字节大端长度N＋N字节正文。
这只是教学方案，不是GT02已经选定的服务器协议。

```text
00 05 48 45 4C 4C 4F   00 05 57 4F 52 4C 44
长度5  H  E  L  L  O   长度5  W  O  R  L  D
```

应用解析器的工作：

1. 不够2字节头部就等待。
2. 读出N，校验不超过协议允许的最大报文。
3. 不够2＋N字节就保留已有内容，等待后续输入。
4. 完整时交付正文，并继续处理缓存中的下一条报文。

N为0时若协议允许空报文，仍要消费2字节头部，保证解析推进。
这里不因为教学方便就为正式产品新增CRC、重传或密码学设计；真实协议要按产品需求另行确定。

### 8.4 设计取舍D08：业务报文怎样分帧？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 换行分隔的文本消息 | 便于调试 | 正文中的换行需转义/限制，仍要处理编码与最大行长 |
| 长度头＋正文 | 可承载二进制，增量解析清楚 | 长度错误需防越界，失步后的恢复规则要另定 |
| 直接使用既有产品协议 | 兼容旧平台，不重复设计 | 必须正确实现其边界、转义和版本规则 |

**GT02优先兼容需要保留的旧产品协议；长度头只用于学习。** 若平台协议已经规定分帧，不要在网络服务里再套一层自创格式。

**自问：一个DATA通知里能不能包含半条业务报文，或者两条业务报文？都可能。**

## 9. TCP连接与发送：一项业务操作可能跨越多个AT阶段

### 9.1 先区分“模组接受命令”和“远端操作完成”

下面仍是教学协议，不是实际NT26指令：

```text
MCU → AT+OPEN=2,"server.example",1234
模组 → OK
……过一段时间……
模组 → +OPEN_RESULT:2,0
```

这里约定OK只表示命令被接受；`+OPEN_RESULT`才报告连接2最终成功或失败。
因此存在两个不同对象：

```text
AT总线事务：发送OPEN → 等待OK → 结束当前命令交互
TCP打开操作：请求开始 → CONNECTING → 等结果URC → CONNECTED或FAILED
```

不能把它们合成一个“收到OK就全成功”的布尔变量。
上层的连接操作应保持待完成记录，直到真正的结果或操作超时到达。

示例只展示一种顺序。真实模组的异步结果可能很快、甚至在命令结束响应附近交错到达，
待完成记录和关联信息要在发命令前准备好，不能收到OK之后才开始登记。
哪些组合才算成功，由该操作的协议契约定义。

### 9.2 网络状态与TCP状态也不是一回事

```text
AT可通信
   ↓
SIM就绪
   ↓
注册查询符合要求
   ↓
数据上下文可用
   ↓
指定TCP连接成功
   ↓
指定业务报文被平台确认
```

每一层都增加了一个条件。前一个条件成立，不自动推出后一个条件成立。
当前实板通过的是前面查询路径，APN/PDP及TCP尚未实测。

### 9.3 发送有自己的小状态机

```text
QUEUED
  ↓ 获得AT发送权
发送SEND命令
  ↓ 等待该操作规定的提示符
发送N字节载荷
  ↓ 等待模组规定的发送结果
成功／失败／结果未知
```

从SEND命令开始，到提示符、载荷、规定的事务结束边界，是一个受保护过程。
其他线程不能在载荷中间插入`AT+CSQ`，否则它可能被模组当作要发给服务器的正文。

“模组报告发送成功”究竟表示进入内部缓存、已发出还是其他阶段，要查手册，不能仅靠`SEND OK`字样推断。
即使模组确认了发送，也没有证明服务器业务已经处理；业务应答由上层协议识别。

注意发送阶段和接收解析模式是两根不同的轴：

| 轴 | 例子 |
|---|---|
| 当前发送事务阶段 | WAIT_PROMPT、SEND_PAYLOAD、WAIT_SEND_RESULT |
| RX字节解释模式 | TEXT、等待头部分隔符、RAW_PAYLOAD |

如果模组支持相应交互，等待发送结果时仍可能收到别路DATA载荷。
不能因为MCU正在“发二进制”，就把所有RX也切成“我发出的那些字节”的模式。

### 9.4 设计取舍D09：长连接操作怎样等待？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 发OPEN后一直占用执行者等最终URC | 单路初学版本简单 | 可能让其他在线连接很久无法发送 |
| 释放AT事务，记录pending操作，URC到来再完成 | 长远端等待不必占住短命令执行机会 | 需要关联表、操作截止时间和迟到结果处理 |
| 不管模组限制直接流水发送很多命令 | 看起来并行度高 | 没有可靠回复身份时会串事务，不能凭空假定支持 |

**第一条可用于单路最小验证，目标多路优先第二条，但必须先确认模组允许相应交错。**
“解锁”还不够：如果唯一操作线程仍阻塞在等待URC的函数里，它一样处理不了下一项。
要把长操作拆成可继续的状态，让执行者能返回调度循环。
若模组要求OPEN完成前不能执行其他AT，就应明确限制和上限，不能通过软件抽象伪造并发。

## 10. TCP事件怎样构造：从厂商语法转换成服务能理解的事实

### 10.1 不把原始URC字符串一路传到应用

假设后端收到教学URC：

```text
+OPEN_RESULT:2,0
```

应分几步解释：

1. 按当前模组协议解析：物理连接编号2，厂商结果0。
2. 查询已准备好的操作和连接映射，确认它属于哪次打开请求。
3. 转成统一含义：某逻辑通道的打开操作成功。
4. 给网络服务投递结果事件。
5. 网络服务校验请求和会话是否仍有效，再改变公开连接状态。

如果没有匹配记录，不要猜“这一定是最近一次连接请求”。应记录孤立/过期事件，并按协议决定清理或恢复。

### 10.2 一个足够理解问题的事件草案

以下是教学草案，不是已经加入工程的API：

```c
/* 内部事件类型，不是发送给模组或服务器的报文字段。 */
enum example_net_event_type {
    EXAMPLE_OPEN_DONE,     /* 某次连接操作完成，结果未必成功。 */
    EXAMPLE_TX_DONE,       /* 某次发送操作完成，结果未必成功。 */
    EXAMPLE_RX_AVAILABLE,  /* 指定连接有数据可读。 */
    EXAMPLE_PEER_CLOSED,   /* 对端关闭了指定连接。 */
    EXAMPLE_NETWORK_LOST,  /* 相关连接共享的网络依赖失效。 */
};

struct example_net_event {
    enum example_net_event_type type;
    uint32_t request_id;          /* 关联本地请求；无对应请求的通知可使用保留值0。 */
    uint8_t logical_channel;      /* 逻辑通道；公共事件使用约定的无通道标记。 */
    uint32_t session_generation;  /* 本地会话代次，不能替代线上关联证据。 */
    int error;                   /* 此事件契约中的错误码；不要拿它单独判断所有业务。 */
};
```

正式实现还要给“取消、结果未知、部分进度、数据有效性”等留出准确表达方式，
可以使用带类型的union或专用结果结构，不应把所有情况强行塞成`error=0/1`。
草案刻意不把接收数据指针直接塞进去：RX_AVAILABLE只通知上层读取对应的持久缓存。

不是所有事件字段都同样有效：

| 事件 | 需要的关联 | 谁改变什么 |
|---|---|---|
| OPEN_DONE | 打开请求、逻辑通道、会话 | 服务将CONNECTING改为在线或失败 |
| TX_DONE | 发送请求、通道、会话、结果阶段 | 服务结束请求；业务层再决定平台ACK |
| RX_AVAILABLE | 通道、会话；不一定有请求编号 | 消费者读取数据，不直接宣布一条业务报文完整 |
| PEER_CLOSED | 当前可确认的通道/会话 | 服务让该路离线，处理其未完成请求 |
| NETWORK_LOST | 受影响的公共网络上下文 | 服务使相关连接失效，恢复公共依赖 |

### 10.3 事件、结果、完成通知、状态的关系

```text
事件：连接结果到了
    ↓ 查证归属并处理
结果：请求201打开连接成功
    ↓ 向请求者交付一次完成通知
状态：逻辑通道1现在在线
```

收到事件不等于不经检查直接覆盖状态；完成也不等于成功，失败/取消同样是终态。
一个请求可能内部发出多条AT，应用只需要收到它自身约定的最终结果，不必为每条AT建立一个业务请求。

### 10.4 设计取舍D10：事件怎样从底层交给服务？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 回调直接修改全局连接表 | 少一次传递 | 多处写状态、锁与生命周期难审查 |
| 直接调用业务回调完成所有处理 | 延迟短 | 业务慢或重入发AT会堵住解析；回调上下文容易被忽略 |
| 规范化短事件交给状态所有者 | 状态转换集中，便于记录和测试 | 要处理队列满、顺序、数据有效期 |

**当前多连接目标选择第三种。** 同一线程内的短内部调用仍可直接调用，不机械增加队列。
接收回调只解释和报告事实，不替服务决定复位，不替产品协议判断平台业务ACK。

关键完成事件不能“队列满就算了”：可以按最大在途操作预留容量，或把结果保存在操作槽并提供可靠唤醒/扫描机制。
若事件链确实溢出，应有可见的故障锁存和唤醒路径，使服务能终止受影响请求并恢复；只打印一条错误还不够。
数据可读提示可在消费者持续检查缓存可读状态的约定下合并，但有先后意义的连接/完成事件不能随意覆盖。

**自问：PEER_CLOSED没有对应本地主动请求，为什么仍是有效事件？**

## 11. 四条TCP连接：四份会话，共用一个模组入口

### 11.1 先不要把连接编号当串口编号

模组内部维护TCP连接，MCU通过同一条UART请求操作这些连接。
四条连接不需要四个UART，也不必有四个线程。

```text
产品使用者A → 逻辑通道0 ─┐
产品使用者B → 逻辑通道1 ─┤
产品使用者C → 逻辑通道2 ─┼→ 统一调度 → 单一AT入口 → 模组内部各TCP连接
产品使用者D → 逻辑通道3 ─┘
```

实际同时支持多少路必须核对NT26型号、固件和模式；“我们分配了4个数组元素”不是硬件能力证明。

逻辑通道是产品接口，模组编号是后端细节，两者可以不相等。例如教学映射：

| 逻辑通道 | 模组编号 |
|---|---|
| 0 | 2 |
| 1 | 0 |
| 2 | 3 |
| 3 | 1 |

接收URC携带模组编号2时，按这份映射应投递到逻辑通道0，而不是直接把2当产品通道。
如果后端当前恰好一一映射，也不要把这种偶然关系写进所有业务模块。

### 11.2 每路需要保存什么？

最小连接对象包括：启用需求、目标地址/端口、状态、最近错误、会话代次、重连计时及独立TX/RX资源。

```text
公共资源：供电、UART、AT核心、相关数据网络上下文

连接0：状态0、TX0、RX0、目标0、会话0
连接1：状态1、TX1、RX1、目标1、会话1
连接2：状态2、TX2、RX2、目标2、会话2
连接3：状态3、TX3、RX3、目标3、会话3
```

原始UART缓存可以共享，因为其中保存的还只是未解释字节。
解析出连接归属后，数据必须保持逻辑隔离；不能让A的消费者先读走B的数据。

某路离线时怎样处理它的待发请求也要定义：直接拒绝新请求、有限排队，或结束已有请求交业务补传。
不能只因为用了FIFO就自动得到“离线可靠缓存”。

### 11.3 设计取舍D11：每路缓存怎样分配？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 四路共用一个没有归属的业务FIFO | 占用看起来少 | 数据混流，消费者相互抢读，不满足独立会话 |
| 每路独立有界TX/RX | 容量与行为清楚，故障隔离直观 | 某路空闲时，其预留空间不能自动被别路使用 |
| 公共数据块池＋每路队列和配额 | 可提高内存利用率 | 生命周期、配额、公平性与耗尽处理更复杂 |

**第一版优先独立有界资源；测量证明确有浪费后，再考虑共享块池＋配额。**
物理内存能否共享不是关键，关键是归属、顺序和容量保障必须独立。
没有每路配额的公共池，仍可能让一路大流量吃掉所有内存。

如果某路消费者太慢，选择只能是：受协议支持地施加背压、拒绝/暂停相关数据、明确报告数据丢失并关闭/恢复该路等。
不能让解析线程永远等这一路，堵死公共UART；也不能静默覆盖最老字节还声称流完整。

**自问：哪种缓存可以共享，哪种数据必须在逻辑上隔离？**

## 12. 多个AT请求同时到来：调度的是操作，不是几段字符串

### 12.1 为什么加一把UART写锁还不够？

写锁只保护每次write时，可能发生：

```text
任务A：发送SEND命令，释放写锁，等待提示符
任务B：获得写锁，发送AT+CSQ
任务A：获得写锁，发送TCP载荷
```

字节可能没有在单次write内部交叉，但事务阶段已经串了。
锁的范围至少要覆盖“本次协议要求不可穿插的完整阶段”，而不是只覆盖一段字符串。

通用OK通常没有请求编号，任意同时发多条后再“看谁先返回”也无法可靠配对。
第一原则是：**一个共享AT通道在任一时刻只有一个明确的总线事务所有者。**

### 12.2 把并发请求变成排队请求

业务不要直接提交任意AT字符串，而是提交能力请求：

```text
通道0：发送请求A
通道1：发送请求B
通道2：连接请求C
服务自身：状态查询D
             ↓
        准入检查与排队
             ↓
       统一调度器挑选一项
             ↓
    模组后端转换成一个或多个AT步骤
             ↓
      AT执行器执行受控阶段
```

同步发起请求不等于同步写串口；多个任务可以几乎同时提交，但线上的AT执行仍被串行化。
同一个模组上的诊断命令也不能绕过调度器偷偷写UART。

### 12.3 设计取舍D12：从最简单FIFO到多路公平

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 所有请求一个FIFO | 容易实现和追踪 | 大量普通发送可能把控制、短消息压在后面 |
| 各路FIFO＋轮转取任务 | 保持每路顺序，减少独占 | 长短任务耗时不同，按任务数公平不等于按带宽公平 |
| 权重/优先级＋配额或老化 | 可表达报警和吞吐需求 | 需要明确饥饿保护、资源预算和测量，配置更复杂 |

**第一版以每路FIFO＋轮转为主，对必要控制操作保留机会。**
优先级需求确实出现后再加入权重或等待时间老化；不把“报警”理解成可以打断任意正在发送的载荷。

例子：0路有大数据，1路有短报警，2路有心跳。
在模组允许的边界把0路数据分成有界发送块，再轮转到1、2路，比把一大块一直发完更容易控制等待。
分块尺寸必须服从模组上限和内存预算，本教程不随便指定NT26最大长度。

```text
合法切换点：一块载荷对应的受保护发送阶段结束
不合法切换：已收到提示符、只发了一半载荷时，插入另一条AT
```

Zephyr线程优先级和这个调度权重是两回事。提高某业务线程优先级，不会自动让UART事务安全抢占。

### 12.4 队列也要有截止时间和准入规则

任务被接受后，可能依次经历：

```text
排队等待 → 等公共网络条件 → 等AT发送权 → 等提示符 → 等最终结果
```

只限制最后一步3秒，不能证明用户请求最多3秒完成。
建议保留单调时钟的绝对截止时间，每阶段按剩余预算决定还能不能开始。
操作、AT事务、注册等待可以有不同预算，但不能层层各重试十次而没有总上限。

队列满时可以整笔拒绝请求，让调用者决定延后。已经接受的请求，应最终得到成功、失败、取消或未知结果。
不能为接收新请求随意purge已经承诺处理的业务队列。

**自问：四个任务同时调用发送接口，怎样做到“都可提交，但不同时发AT”？**

## 13. 超时、取消、迟到事件：请求结束不代表世界复原了

### 13.1 一个最危险的时间线

```text
t0：发命令A
t1：A等待超时，本地宣布A结束
t2：发命令B
t3：A迟到的OK到达
t4：代码把它当成B成功
```

把信号量清零、增加一个请求编号，并不会在串口里的OK上写上“A的编号”。
**超时表示本地等待预算用尽，不证明模组没有执行，也不证明旧回复不会再到。**

### 13.2 先决定哪些身份是本地可知的

| 身份 | 用途 | 不能证明什么 |
|---|---|---|
| request_id | 区分应用提交的请求 | 不能给无编号的线上OK自动配对 |
| 内部AT事务记录 | 保存当前匹配规则和等待条件 | 不能仅凭“当前”消除旧回复 |
| logical_channel | 表达产品使用的通道 | 不等于模组socket编号 |
| 模组连接编号 | 解释模组URC | 编号复用后，旧URC未必能识别为旧会话 |
| session_generation | 拒绝本地旧会话任务/事件 | 若线上没有代次，不能凭空识别迟到URC属于哪代 |
| 模组生命周期代次 | 模组恢复后整体使旧记录失效 | 仍不能代替真实的串口重同步和安全编号重用 |

这些标识不一定都要在最初实现，随着相应问题出现再加入；但不能用一个字段解释所有身份。

### 13.3 设计取舍D13：超时后怎样继续？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 立即重发或发下一条 | 代码短，表面恢复快 | 迟到响应误关联、命令重复执行、数据重复交付 |
| 等一会儿清缓存后再试 | 某些现场看起来有效 | 没有协议保证时仍不是可靠边界，清缓存还可能丢合法URC |
| 进入不确定/失步状态，按协议恢复后再接新事务 | 结果更可信 | 恢复需要额外状态，可能牺牲一段可用性 |

**选择第三种。** 可用恢复方式可能是协议支持的取消、确认操作状态、已验证的重同步或最终复位；按具体模组决定，不默认每次都断电。
仅发送另一条AT并等OK，也可能接到旧OK，不能当作普遍有效的同步屏障。
当前最小固件选择事务超时后停止本轮，不继续发下一条，是保守边界，不是完整自动恢复。

### 13.4 取消不等于撤销已经发生的事情

请求还在队列里时，取消可以移除它并释放缓冲。
已经进入发送载荷阶段时，不能假设取消就能把线上字节撤回；需要到安全边界或执行协议允许的中止。
已经可能到达服务器时，应报告对应阶段的失败/未知，不谎报“肯定一个字节都没发送”。

UART已发字节数、模组接收字节数、远端TCP收到字节数、平台业务处理数量，是不同层面的量。
只能报告有证据的那个量。新TCP会话也不能自动接着发上一条旧报文的后半段。
业务是否允许重传、怎样去重，应由平台协议的报文编号和幂等规则决定。

### 13.5 本地完成应恰好交付一次

超时计时器和成功URC可能几乎同时到达。
需要在受保护的状态转换中，只允许一个路径把请求从PENDING变成终态，然后通知一次并释放一次资源。

```text
PENDING ─→ SUCCESS
        ├→ FAILED
        ├→ CANCELLED
        └→ UNKNOWN/TIMEOUT
```

这是本地接口的完成约定，不是声称远端服务器获得了“全球恰好执行一次”的保证。
迟到事件可以记录，但不能再次释放同一缓冲、再次调用已完成请求的完成回调。

**自问：加了generation，是否就能知道一个迟到的`closed,2`属于旧socket2？不能，除非还有可靠关联证据或编号重用屏障。**

## 14. 缓冲区属于谁：指针不是数据的所有权

### 14.1 从一个容易忽视的错误开始

应用在函数里创建一个局部数组，调用异步发送接口后立即返回。网络线程稍后才真正发送。
如果队列里只放了这个数组的地址，届时数组可能已经失效，或者被下一次调用覆盖。
即使AT调度完全正确，平台收到的内容仍然会错。

```text
调用线程：创建数组 → 把指针放入队列 → 返回，数组生命周期结束
网络线程：                         取出指针 → 访问已经失效的内容
```

因此每个异步接口都要回答：谁保存数据、谁可以修改、何时可以释放、失败由谁清理。
Zephyr的消息队列会复制固定大小的消息项，但复制结构体里的指针，只是复制地址，不会自动复制指向的数据。
参见[官方消息队列说明](https://docs.zephyrproject.org/latest/kernel/services/data_passing/message_queues.html)。

### 14.2 设计取舍D14：数据怎样进入异步发送队列？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 接口接受时，把载荷复制到服务自有的有界缓存 | 调用者返回后可以立即复用原数组，契约直观 | 占用额外缓存和复制时间；超长数据必须拒绝或分块 |
| 借用调用者缓存，直到完成通知后才归还使用权 | 可以减少复制 | 调用者必须一直保持有效且不修改，取消和超时也要明确归还时刻 |
| 从共享内存池申请块，再把块的所有权交给服务 | 适合高吞吐、减少重复复制 | 需要句柄、引用/归还规则、各连接配额和泄漏诊断 |

**当前建议先用第一种。** 接口返回“已接受”时，表示已经成功保存全部待发送数据；容量不足就整笔拒绝。
这适合先完成小报文和单连接闭环。未来测出复制成本确实成为瓶颈，再考虑内存池。
不必因为分了三层，就在三层各复制一遍；确定一个清晰的数据主人即可。

接收方向也一样。解析器临时缓冲中的地址不能随事件排队后继续被覆盖。
可以先把数据复制到该连接的RX缓存，再通知服务“这条连接现在有数据可读”。
如果采用内存池句柄，必须写清楚消费者处理完后怎样归还。

### 14.3 有了缓存，不代表不会溢出

以115200波特、8N1为教学算例：一个字节占1个起始位、8个数据位、1个停止位，共10位。
理论单方向上限为11520字节/秒；2048字节缓存只对应约178毫秒的持续满速输入。
这是理想容量算式，不是“线程可以放心停178毫秒”的保证：已有积压、调度延迟、URC和日志开销都要考虑。

RTT输出与模组UART并非同一条通信线路，但日志仍消耗CPU时间和日志缓存。
把所有原始载荷都打印出来，可能恰好让接收变得不可靠。
没有实际接线和驱动配置证据时，也不能假设RTS/CTS会替你阻止模组继续发送。

RAM预算至少包含：

```text
线程栈 + UART原始环形缓冲 + 解析器存储
+ 各连接TX/RX配额 + 请求/事件队列 + 未完成操作记录 + 日志等系统开销
```

容量要根据报文上限、突发量和最坏消费延迟估算，再通过高水位统计调整。
“四条连接各分4 KiB”可以是实验参数，不能在没有业务数据时当成产品标准。

**自问：异步接口把一个指针放入k_msgq，是否就可以立即释放原数组？不可以，除非接口已经另行复制数据。**

## 15. 层级怎样通信：函数、队列、信号各有用途

### 15.1 分层不等于每一层创建一个线程

层回答“谁负责什么”，线程回答“谁可以在什么时候执行”。
例如操作线程调用Lierda后端，后端再调用通用AT执行器，这三段可以是同一线程里的普通函数调用。
只有需要跨执行上下文，或需要解除等待关系时，才有必要引入队列和通知。

### 15.2 设计取舍D15：用几个执行上下文？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 一个循环包办收串口、等待AT、服务状态 | 代码集中，初看最简单 | 一旦阻塞等回复就可能停止接收；需要把所有操作改成非阻塞状态机才能可靠工作 |
| 接收解析线程＋网络工作线程 | 容易理解，适合当前AT查询验证 | 网络线程阻塞等待长操作时，不能及时处理新的服务命令 |
| 接收解析线程＋操作执行线程＋服务状态线程 | 等待AT时仍能接收字节和处理服务需求 | 增加栈和队列，必须定义状态归属与跨线程生命周期 |

**当前验证保留第二种；进入多连接和生命周期管理时，再按需要采用第三种。**
如果改用成熟的全异步事件循环，也可能用较少线程实现同样隔离，代价是更多状态机代码。
不要为了形式完整，现在就把每个小函数都做成消息。

目标通信关系可以这样看：

```text
应用线程
  │ 提交连接/发送/停止需求，接口只做校验和入队
  ▼
服务线程：持有公开状态、连接需求和调度策略
  │ 操作请求队列                         ▲ 归一化事件队列
  ▼                                      │
操作线程：后端操作 → AT执行器             │
  │ 发命令/载荷          ▲ 事务完成通知    │
  ▼                      │               │
UART驱动 ←──────── 接收解析线程 ──────────┘
  ▲                      ▲
  └─ UART中断复制字节 → 原始环形缓冲＋唤醒
```

箭头表示不同性质的通信：同线程能力调用可以直接调用函数；跨线程请求/事件用有界队列；
一个正在等待的事务可以通过专用结果槽加信号量唤醒。
**不要让操作线程必须等待服务线程处理完成事件，而服务线程又同步等待这个操作线程返回。**

### 15.3 一个状态应有一个明确的修改者

| 对象 | 建议的主责 | 其他上下文怎样访问 |
|---|---|---|
| 对上层公开的网络和逻辑连接状态 | 服务线程 | 发事件请求更新；查询读取受保护快照 |
| 厂商连接编号与操作记录的映射 | 后端内部 | 解析和执行路径通过明确的锁/发布协议访问 |
| 当前AT事务的结果与终态 | AT执行器内部 | 接收路径更新结果并通知等待者，终态转换受保护 |
| UART字节环形缓冲 | 中断生产、解析线程消费 | 满足单生产者/单消费者及内存可见性约定 |
| 各连接待发送业务数据 | 服务/队列所有者 | 执行者取得明确使用权，完成后按契约归还 |

“主责”不是假装只有一个上下文碰到数据，而是规定谁能做决定、哪些并发访问必须协调。
锁只保护必要的共享字段；不能在长时间等待AT时一直持有服务状态锁。
解析回调只做短处理，也不能在系统工作队列中长期阻塞整个网络流程。

**自问：一次完成通知应该先经过服务线程再唤醒AT等待者吗？不一定；如果形成循环等待，就需要直接的事务完成通道。**

## 16. 什么时候上电、复位、断电：这是资源生命周期问题

### 16.1 从产品需求推导控制权

假设通道0上传完成，通道1还在接收平台命令。通道0不能直接把模组电源关闭。
电源是四条连接共享的资源；“某条连接不用了”和“整个模组不用了”是不同条件。

```text
应用：我需要通道0在线 / 我不再需要通道0
             ↓
服务：汇总全部连接和其他功能的需求，决定模组是否仍需工作
             ↓
后端：执行该型号的正常关机、开机、复位等具体操作
             ↓
硬件适配：操作板上实际存在的GPIO、UART和电源控制
```

### 16.2 设计取舍D16：谁决定生命周期？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 每个应用模块直接调用电源GPIO | 最快看到硬件动作 | 多连接互相断电，无法统一取消、状态和恢复 |
| 底层任何错误都自动复位/断电 | 单条测试程序看起来容易自愈 | 一条链路故障拖垮全部链路；应用不了解数据是否已发送 |
| 服务汇总需求和恢复策略，后端执行具体机制 | 能协调共享资源、给出一致状态 | 要建立有限状态、停止规则和恢复边界 |

**选择第三种。** 底层可以报告“UART已失效”“AT同步不可信”“模组意外重启”，
服务根据影响范围决定何时恢复。后端仍负责设备手册规定的时序和必要的内部步骤。
这样既不把GPIO细节泄漏给服务，也不让底层擅自替整个产品决定断电。

### 16.3 两类状态机，不要塞进同一个枚举

模组/公共网络状态的教学示意：

```text
OFF → STARTING → WAIT_SIM → WAIT_REGISTRATION → ACTIVATING_DATA → READY
 ↑                                                               │
 └────────────────── STOPPING ← 无需求或停止请求 ─────────────────┘

任一失败 → 分类处理 → 有限退避 / 等待外部条件 / 明确失败
```

每条连接独立具有：

```text
DISABLED → WAIT_NETWORK → CONNECTING → ONLINE → CLOSING
                ↑            │          │          │
                └── BACKOFF ←┴──────────┘          └→ DISABLED或重新等待
```

这些是解释用状态，最终实现可根据需求合并，不要求机械照搬。
SIM未插入适合等待条件改变；信号差适合有限退避；单个服务器关闭连接先处理对应连接；
只有证据表明公共模组状态失效时，才考虑影响全部链路的恢复。

服务决定“确保网络可用”，后端提供型号相关的数据连接能力。
某些模组自动激活数据上下文，另一些需要显式配置、激活和结果等待。
统一上层意图，不代表要求所有后端具有完全相同的AT步骤数量。

### 16.4 停止也要有过程

正常停止应停止接受新数据，按策略处理已接受任务，关闭连接，执行模组支持的正常关机，最后按硬件要求关闭供电。
如果电量已经触发紧急断电策略，可以走明确的强制路径，但要把未确认操作报告为失败或未知。
不能把强制切电伪装成所有请求都正常完成。

服务线程可以在AT执行期间接收“停止”需求，但不意味着可以立即打断载荷发送。
实际停止需要等安全边界，或者执行后端明确支持的中止/恢复流程。
重复的“确保启动”应合并为同一目标，不能每次都重新拉一遍PWRKEY。

模组复位后，旧连接映射、未完成操作和旧事件都需要失效处理；UART何时停收、清理和重新初始化也要明确。
PCB没有接出的RESET、STATUS或流控脚，软件不能通过抽象接口凭空获得。

**自问：一个连接需要重连，是否应该复位整个模组？通常先做该连接的恢复；全局恢复需要相应证据和策略。**

## 17. 回到GT02：怎样分层，换模组时才不会重写整个服务？

### 17.1 先把变化原因分开

下列变化并不是同一种变化：

| 变化 | 理想情况下主要修改的位置 |
|---|---|
| 同一模组换了PCB，UART和控制脚改了 | 板级DTS、pinctrl和必要的硬件适配 |
| 模组从Lierda换成另一厂家，命令/URC/电源时序不同 | 厂商后端、能力描述及相关时序配置 |
| 某服务器改地址、某通道改变重连间隔 | 服务配置/策略 |
| 平台报文格式、报警内容改变 | 产品业务及平台协议组件 |
| UART由中断方式升级成异步API | 硬件字节传输适配，及必要的缓冲契约调整 |

这是目标边界，不是“换任何模组都完全不动其他代码”的保证。
如果新模组根本不提供四连接、主动接收或相同的安全能力，服务必须识别能力差异，产品也要重新验收。
统一接口能隔离语法，不能创造硬件没有的功能。

### 17.2 设计取舍D17：共用流程放在哪里？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| UART、AT、厂商命令、联网和业务都放在一个文件 | 最初一个AT测试很快写完 | 同一文件同时因引脚、模组、平台而变化，替换影响大 |
| 每个动作建立一层包装，所有调用逐层转发 | 看起来层级齐全 | 大量只改名字的函数，定位困难，共用机制仍可能重复 |
| 服务保留意图和策略，AT核心共用机制，后端实现具体操作，硬件层搬运字节 | 可复用事务与调度，变化边界清楚 | 要认真定义能力、结果、事件和数据生命周期 |

**建议第三种，但按实际复杂度逐步拆。** 抽象的目的，是让某种变化只影响有限范围，不是让文件数量更多。

```text
产品应用/平台协议
  │ 逻辑通道、业务载荷、平台确认
  ▼
网络服务：何时联网/断开、各通道状态、调度、重连和恢复策略
  │ 统一能力：查询SIM、确保数据连接、打开/发送/关闭连接
  ▼
厂商后端：具体命令、参数、响应、URC、连接编号和设备内部步骤
  │ 请求AT事务、接收解析结果，必要时切换定长载荷模式
  ▼
共用AT机制：事务串行化、匹配生命周期、等待条件、超时、文本/载荷状态
  │ 字节读写/通知                    ▲ 字节
  ▼                                │
硬件适配：UART、GPIO、电源控制执行；板级DTS说明接在哪里
```

这里的“共用AT机制”可以封装Zephyr已有处理器，不等于必须自己重写AT解析器。
不同后端提供语法规则和操作步骤，共用核心提供安全执行规则。
现有SDK处理器是否足以支持所选二进制路径，应通过对应源码、模组协议和测试确认，不能由图直接推定。

共同流程例如“网络不可用就等待/恢复”“连接失败按预算重试”属于服务。
“这个型号打开连接前要先选择上下文”“这条发送命令需要提示符”属于后端操作实现。
服务不应该为了复用流程而亲自判断某厂家回复中的逗号位置。

第一版只支持一个后端时，统一函数由编译期选中的实现提供就够了。
真正需要同一固件支持多个型号、运行时选择时，再考虑操作函数表。
不要把运行时插件框架当成实现可替换性的前提。

### 17.4 重建前的真实调用链（历史）

```text
main / 应用初始化
  → gt02_network_service_start()
  → 启动network_thread（当前也充当操作执行者）
      → gt02_modem_init()
      → gt02_modem_power_on()，启动modem_rx_thread
      → gt02_modem_handshake()：AT、ATE0
      → gt02_modem_identify()：ATI
      → gt02_modem_query_status()：CPIN、条件满足后CSQ、CGREG
      → 保存成功/等待结束/失败状态，本轮后台流程结束

并行接收路径：
UART中断 → 环形缓存 → modem_rx_thread → SDK命令处理器 → 回调/完成信号
```

目前没有“每条TCP一个线程”，也没有四连接队列。
当前两个相关线程的栈分别由`CONFIG_GT02_NETWORK_STACK_SIZE`和`CONFIG_GT02_MODEM_RX_STACK_SIZE`控制。
这是配置入口；最终构建值应查看对应构建目录的`zephyr/.config`，不能只看某个文件里最后写过的值。

`modem_cmd_send_nolock()`的第一个参数是字节接口，提供读取/写出等能力；另一个参数是命令处理器。
两者共同参与一次命令交互。它不是“传入第一个参数，就自动建立了全部线程安全机制”。
当前`command()`在外部取得发送锁，再调用这个函数，最后释放锁。
`nolock`表示该入口不替你取得那把发送锁，**不表示函数不会等待回复**。

当前`response_text()`只服务指定的零参数文本回调，通过“前缀长度＋当前有效长度”补字符串结束符。
这解决的是本工程曾经遇到的旧尾部残留问题，不是可以套在所有SDK回调、DIRECT或二进制上的万能模板。
前面第6章还提醒：临时匹配表的更新/移除需要核对并发协议，不能只因为接口来自SDK就假定一切安全。

### 17.5 现有日志证明到哪里？

```text
AT、ATE0、ATI成功      → UART和基础命令正常路径走通
+CPIN: READY + OK     → 本轮SIM查询正常
+CSQ: 18,0 + OK       → 收到可解析的信号质量等级
+CGREG: 0,1 + OK      → 本轮旧CGREG查询报告本地注册
```

这些日志没有证明APN/PDP、TCP连接、二进制收发、四路并发、长期重连或断电恢复已经完成。
旧的CPIN解析失败日志与修复后的成功日志属于不同代码阶段，也不能混成“当前仍然一定失败”。
Flash启动失败需要单独定位；它既不能证明4G失败，也不能被4G成功日志掩盖。

**自问：换模组时，服务是否还应该匹配`+QIURC`或判断ATI包含Lierda？目标设计中不应该；当前最小验证中的这类假设要在扩展时逐步下移。**

## 18. 怎样证明自己真的理解了：从小实验到异常验证

### 18.1 设计取舍D18：怎样验证协议代码？

| 思路 | 优点 | 代价/局限 |
|---|---|---|
| 编译通过就接入产品 | 快 | 不能证明分片、归属、超时和数据正确 |
| 只在真模组上测试一次正常连接 | 能验证真实接线和一条正常路径 | 极难稳定复现迟到、交错、队列满和特定二进制内容 |
| 字节回放验证解析/调度，再用真模组验证协议与时序 | 错误可重复、边界可覆盖，也保留真实硬件证据 | 要把可测试的边界留出来，准备输入和预期结果 |

**建议第三种，按功能增量验证。** 先回放不依赖硬件的协议机制，再做真实模组端到端验证。
回放通过不代表供电、UART错误恢复和实际厂商语法通过；实板一次成功也替代不了回放边界测试。

### 18.2 八个递进练习

| 练习 | 给系统什么输入/条件 | 应当观察到什么 |
|---|---|---|
| A：AT最小事务 | 把`\r\nOK\r\n`拆成各种读取批次 | 恰好一次成功，不能少通知或重复通知 |
| B：查询数据 | READY＋OK；只有OK；格式错误＋OK；ERROR | 只有满足查询契约的第一种成功，其余得到明确失败，下一次事务不继承旧结果 |
| C：URC插入 | 在CSQ响应前后插入教学关闭事件 | CSQ结果正确，只更新对应连接，不能把URC当查询字段 |
| D：提示符 | `>`没有换行、与其他字节同批；非等待阶段出现`>` | 仅在合法发送阶段触发载荷发送，载荷不能发两次 |
| E：二进制 | 第7章8字节载荷，任意分片，含NUL/CRLF/OK/`>` | 按长度还原8字节，载荷内部不产生AT成功或提示符事件 |
| F：会话归属 | 映射表变化、旧会话本地事件、重复完成 | 更新正确逻辑通道，拒绝已识别的旧会话事件，完成和释放各一次 |
| G：四路调度 | 四路都有数据，一路持续繁忙，一路消费很慢，队列填满 | 不串数据；满足所选公平规则；慢消费者不堵死解析；新请求按容量契约接受/拒绝 |
| H：超时与停止 | 晚到OK、打开连接超时后收到结果、发送中停止、模组重启 | 不把旧OK当新成功，不虚报未发送，资源最终归还，恢复有上限 |

练习C/D/E使用前文的教学语法，真实后端回放要换成核对过的模组报文。
对于线上没有代次的迟到URC，练习F不能期待软件“凭空认出”，而应验证编号复用/恢复屏障。

练习E还要覆盖：头部CR和LF分批、载荷第一个字节就是CR或LF、长度恰好等于上限、超出上限、畸形数字。
长度为0时是否允许，以及如何处理尾部，按具体语法给出预期；如果不允许，应明确拒绝并恢复同步。
不要只测试容易展示的ASCII文字。

### 18.3 一个非常有价值的性质：切分方式不改变协议结果

```text
同样的线上字节序列：
一次喂入全部字节
每次喂入一个字节
从任意位置分成两段
随机分成多段

预期：识别出的事务结果、事件归属、重组后的载荷字节一致。
```

这不要求所有日志时间戳、回调批次数完全相同；允许数据回调按不同块大小出现。
要求的是合并后的数据顺序、内容和语义一致。
超时测试则另外控制时间和调度，不能把“等待间隔已经超过协议预算”当成单纯分片。

### 18.4 日志应该帮助重建因果关系

只记录“发送失败”不够。建议逐步保留：

```text
t=12345 req=37 logical=1 wire=0 gen=6 stage=WAIT_PROMPT
t=12348 req=37 logical=1 wire=0 gen=6 stage=PAYLOAD_TX bytes=120
t=12370 req=37 logical=1 wire=0 gen=6 stage=MODEM_RESULT result=SUCCESS
```

这是建议的调试字段，不是当前已经输出的格式；不同模组成功结果的准确含义仍按手册定义。
业务确认应另记为平台协议事件，不能和第三行合并。

有用的统计包括RX环形缓存高水位/溢出、各连接队列高水位、解析错误、事务超时、迟到事件、关键事件投递失败。
关键事件丢失不是一个可以忽略的普通计数，需要按第10章的完成保证进入明确故障处理。
“线程还在跑”与“请求持续取得进展”也要分别观察。

文本阶段可用整行日志；二进制阶段用长度和受限十六进制片段核对，不能`%s`输出任意字节。
实际产品还应能关闭原始日志，并避免把PIN、凭据、用户数据长期写入日志。

本文本次交付只验证文档结构、链接和教学样例一致性；没有因此完成上述固件回放或实板验收。

## 19. 把所有概念串起来：综合推演与后续路线

### 19.1 一个完整情景，逐步判断谁来处理

假设四条逻辑连接已经在线，业务同时提交多项发送任务。以下仍然使用教学协议，不是NT26命令时序。

```text
时间      服务/操作线程                     接收解析线程
t0        接受连接0/1/2/3的发送请求           持续接收
t1        调度连接0，发送对应SEND命令
t2                                        识别提示符，通知当前事务
t3        发送连接0的完整载荷                  收到连接2的关闭URC
t4                                        映射成连接2的关闭事件交给服务
t5                                        收到连接1的数据头，切入定长模式
t6                                        载荷中的OK/CRLF只算数据，放入连接1 RX缓存
t7                                        按语法回到文本模式，识别连接0发送结果
t8        当前受保护阶段结束                 服务处理对应结果和RX通知
t9        调度下一项合法操作                  连接2按策略进入重连/退避
```

这段情景有一个必要前提：真实模组允许这些异步交错，并给出了可解析的边界。
如果厂家规定发送载荷期间不插入某类接收，后端按该规定实现；软件不能自己假定任意交错都可识别。

沿着这个故事，检查下面几件事：

1. 连接2关闭，改变的是连接2状态，不是把四路都标成断开。
2. 连接1载荷中的`OK`不是连接0发送成功。
3. 连接0的发送阶段未结束时，不能插入连接3的新AT命令。
4. 四个业务提交可以都被接受，但接受的前提是各自数据已经按契约保存。
5. 连接2恢复不能让旧会话剩余的半条业务报文直接拼进新会话。
6. 连接0得到模组发送成功后，平台是否处理完成仍由业务协议确认。
7. 如果线上状态失去可信边界，暂停新事务并恢复，比猜一个成功结果更可靠。

### 19.3 先独立回答，再对照答案

| 问题 | 参考答案 |
|---|---|
| 为什么不能每次UART读到东西就当成一条回复？ | 读取批次没有协议边界保证，同一行可能跨批次，多条消息也可能同批到达 |
| 信号量唤醒是不是就表示成功？ | 不是；它只表示有结果/条件变化，还要读取受保护的结果 |
| 查询收到了OK就足够吗？ | 不够，还要验证本查询要求的数据确实收到且有效 |
| URC是不是都以加号开头？ | 不是，RDY就是反例；查询数据也常以加号开头 |
| 为什么解析回调中不直接发另一条AT并等待？ | 当前接收线程可能被自己堵住，后续回复无人处理，且可能破坏事务串行化 |
| 二进制中的OK怎样区分？ | 定长载荷阶段只消费规定字节，不用文本关键字判断 |
| 模组一次上报120字节，是不是平台的一条完整报文？ | 不一定；TCP是字节流，业务报文按自己的协议重组 |
| 四条TCP为什么不用四个读UART的线程？ | 共享一条字节流，多读者会拆散数据；应先统一解析再按连接分发 |
| 锁住UART发送函数够不够？ | 不够，必须保护从命令到提示符、载荷及相关结果的协议阶段 |
| 本地request_id能解决迟到OK吗？ | 不能，线上OK没有这个编号；必须有可信恢复和关联边界 |
| generation能解决所有迟到URC吗？ | 不能；本地已标识的旧事件可拒绝，但无线上代次的URC还需要关联/复用屏障 |
| SEND成功是不是平台已处理？ | 不是，准确含义看模组手册；平台处理确认属于业务协议 |
| 取消是不是等于没有发送？ | 不是，已上线路的数据不能撤回，要报告已知进度或未知结果 |
| 换模组为什么仍然可能要修改服务？ | 能力或业务语义确实变化时需要适配；抽象隔离语法，不能掩盖能力不足 |

如果某个答案还无法自己解释，回到对应章节，用纸画出字节流、事务和线程，通常比继续记API更有效。

### 19.4 这个工程接下来怎样一步步落地？

| 阶段 | 只增加的核心能力 | 完成标准 |
|---|---|---|
| 1：巩固AT基础 | 保留已走通查询，确认事务/临时规则并发和失败边界 | 拆分输入、缺数据、格式错误、晚到响应有明确预期，不破坏已通过路径 |
| 2：生命周期闭环 | 服务接受需求，完成可重复启动/停止与有限恢复 | 冷启动、正常停止、再次启动及失败清理可验证，不影响LED/其他任务 |
| 3：单连接TCP | 核对NT26手册和实测报文，完成数据上下文、打开、收发、关闭 | 真实服务器双向字节正确，含NUL/CRLF，断链归属清楚 |
| 4：四连接 | 独立缓存/状态、映射、统一执行和公平调度 | 在确认模组支持的前提下，四路不串数据，一路故障不会无故终止其他链路 |
| 5：产品可靠性 | 断网、超时、队列满、慢消费者、取消、复位与平台确认 | 恢复有上限、内存有上限、结果不虚报、状态可追踪 |

每阶段可以再拆小步，不要求一次提交完成整行。
例如生命周期阶段先定义停止结果，再实现正常关机，最后增加异常恢复；单连接先打开关闭，再加文本收发，最后验证任意二进制。
不要为了接近最终图，先建一批空文件、枚举和函数指针，而没有一条真实可验证的路径。
