## 1. 先记住这五句话

1. **业务层决定产品要做什么**：什么时候上传、上传什么、平台怎样确认。
2. **网络服务组织四条连接**：状态、队列、调度、重连和对上层的结果通知。
3. **Lierda适配层完成具体模组操作**：命令、响应、URC、载荷和上电时序。
4. **Zephyr驱动搬运字节、控制电平**；DTS只说明硬件接在哪里。
5. **四条TCP逻辑独立，UART和AT通道统一受控**；四连接不等于四个UART或四个线程。

## 2. 目标、范围与当前事实

### 2.1 设计目标

- 三条现有需求连接以及第四条扩展连接使用同一套接口，每条可独立启停和收发。
- 各连接拥有独立的数据归属和容量限制，一条连接异常不随意影响其他连接。
- 更换PCB主要修改DTS；更换同类模组主要修改适配层；更改平台报文不修改模组驱动。
- 所有操作有明确结果、资源上限和超时，网络异常不阻塞IMU采样与产品事件处理。
- 先建立最小可运行链路，再逐步达到旧工程完整业务能力。

### 2.2 当前事实与待确认项

- 当前已有 `modem0` 私有接线描述、UART1及控制GPIO，详见硬件接口文档。
- UART1已在S1中改为 `okay` 加 `zephyr,deferred-init`，由适配层在模组上电后初始化；S1尚待实板验收。
- 旧工程 `appcom/netmod/netmod.h` 中 `NETMOD_CONNECTION_MAX` 为3；这是软件配置，不是模组能力上限的证明。
- 旧 `netmod_module_lierda.c` 使用 `QICSGP`、`QIACT`、`QIOPEN`、`QISEND`、`QICLOSE` 等命令。
- 旧Lierda接收实现读取 `+QIURC` 中的连接编号和长度，再切换到定长载荷接收。
- 用户ATI日志已确认NT26-KCN、固件NT26KCNF20NNA-Q02011622；最大连接数、各类长度和时序仍需对应手册确认。
- 四连接是软件设计目标；必须确认实物同时支持至少4条所需TCP连接后，才能承诺实板能力。

### 2.3 第一阶段不做什么

不接PPP，不先实现完整Socket Offload，不一次加入TTS、短信、GNSS、TLS、OTA或所有AT命令。
这些能力不是被取消，而是在对应产品切片中按需求补齐。

## 3. 总体结构与依赖方向

```text
产品应用／平台协议
        ↓ 逻辑连接请求、待发送字节
网络服务
  ├─ 连接0：状态、配置、TX队列、RX缓存
  ├─ 连接1：状态、配置、TX队列、RX缓存
  ├─ 连接2：状态、配置、TX队列、RX缓存
  ├─ 连接3：状态、配置、TX队列、RX缓存
  └─ 公共网络流程、发送调度、恢复策略
        ↓ 通用模组能力接口
Lierda适配层
  ├─ AT事务执行与结果分发
  ├─ Lierda响应、URC和定长载荷处理
  └─ Zephyr UART／GPIO访问及硬件时序
        ↓
Zephyr UART／GPIO驱动 ← 板级DTS与pinctrl
```

请求自上而下；结果、状态变化和数据通过约定的事件或接口向上传递。
适配层不能包含具体报警、平台协议或产品状态机头文件。

`interfaces/` 存放必要的能力契约和类型，不是额外运行的中转组件；
平台协议编解码可以放入 `lib/`，由业务使用，也不必机械增加一层线程或服务。

## 4. 每个层级负责什么？

| 层级 | 负责 | 不负责 |
|---|---|---|
| 产品应用／业务 | 联网需求、上传内容与时机、逻辑通道用途、报警、平台应答、离线补报策略 | AT字符串、物理GPIO、UART实例、模组socket编号 |
| 网络服务 | 四连接配置与公开状态、TX/RX队列、发送调度、联网流程、有限重连与退避 | 解释Lierda参数、直接解析UART流、直接访问引脚 |
| 模组能力接口 | 上电、查询、数据连接、TCP操作与事件的语义、错误及数据生命周期约定 | 复制一份状态机或提供万能原始AT业务入口 |
| Lierda适配 | 执行具体命令、等待操作结果、解析URC和载荷、映射连接编号、执行硬件时序 | 平台选择、业务优先级、报警判定、无限重连 |
| Zephyr驱动 | UART收发、GPIO配置和电平操作、硬件错误反馈 | 理解AT响应、TCP会话和产品报文 |
| DTS／pinctrl | 控制器、引脚、默认串口参数、控制信号极性和稳定别名 | 上电程序、运行时连接状态、重试策略 |

### 4.1 产品应用与协议模块

业务决定“需要把这条报警交给哪个逻辑连接”，协议模块把报警编码成字节。
网络服务不需要知道报文中的经纬度、报警字段和校验规则。

接收方向相反：协议模块从该连接字节流中组包、校验、提取命令，业务决定如何执行。
一段TCP载荷不是天然完整的产品报文；断线后是否补传、怎样去重，也属于上层语义。

### 4.2 网络服务

网络服务是对上层公开连接状态的唯一管理者，拥有连接配置、退避计时和发送调度。
它决定何时请求数据连接、何时连接服务器、失败后等待多久以及是否请求模组恢复。

服务只调用“激活数据连接”“连接目标”“发送字节”等能力，不拼接 `AT+QIOPEN`。
一条连接失败，先处理这条连接；只有公共资源失效时，才组织所有受影响连接恢复。

### 4.3 Lierda适配层

适配层把通用请求转换为该型号的实现，并记录操作所必需的临时状态：
当前AT事务、等待的结果、逻辑句柄到模组编号的映射、当前定长载荷的剩余字节数。

例如“连接一次”可能经历：发送命令、收到接受响应、等待连接结果URC、成功或超时。
这是操作内部进度，不是服务层的重连策略。失败后如实报告，不私自永久循环。

底层GPIO和AT机制可以拆文件，但不为每个函数都增加包装。模组适配中的厂商依赖不向业务泄漏。

## 5. 状态和资源分别由谁拥有？

| 状态／资源 | 逻辑所有者 | 访问约定 |
|---|---|---|
| 产品工作模式、报警与平台应答 | 产品业务／对应协议服务 | 网络服务只接收请求与传递字节 |
| 公共网络流程、四连接公开状态 | 网络服务 | 其他模块通过命令、快照和事件访问 |
| 每连接待发队列、接收缓存、调度权重 | 网络服务 | 提供受同步保护的有界入队／出队入口 |
| 当前AT事务、模组编号映射、解析状态 | 模组适配 | 回调产生操作结果，不直接改服务的连接表 |
| 公共UART接收缓存及接收缓冲生命周期 | 硬件适配部分 | UART回调搬运，解析线程消费 |
| 物理接线 | 板级DTS | C代码通过描述获取，不复制引脚常量 |

“所有者”是职责归属，不表示只有一个线程能接触所有缓存。
例如解析线程可以通过网络服务提供的非阻塞入队入口交付载荷，但不能任意修改其状态字段。
跨线程队列、快照及缓冲释放必须有明确同步方案，不以 `volatile` 代替同步。

## 6. 公共状态与四连接状态

公共流程按“关闭、启动中、等待注册、激活数据连接、网络可用、恢复／退避”组织。
这里规划共享网络上下文；具体上下文编号与APN设置由适配实现并按模组能力核对。

每条连接独立维护“停用、等待网络、连接中、在线、关闭中、退避等待”等状态。

- TCP单路断开：更新该路，通知其使用者，按该路策略恢复。
- 数据连接失效：全部相关TCP标记不可用，先恢复公共依赖。
- 模组重启：旧映射与未完成事务全部失效，不能继续报告旧连接在线。
- 某路没有发送数据：不等于其他路可以关闭模组；关机要协调所有使用请求。

连接对象至少包含逻辑通道、启用标志、目标地址／端口、状态、最近错误、重连计时、
独立TX/RX资源、调度参数和会话代次。通道用途由产品指定，不预设“连接0一定是报警”。

会话代次可以拒绝本地过期任务，但不能凭空区分模组协议中没有代次的迟到URC。
编号重用必须结合关闭确认、事务清理及必要的重新同步；不能只加一个计数器就宣称安全。

## 7. 线程与执行上下文

多连接目标按下列三个上下文规划。这是执行模型，不是三个新增软件层，也不是四连接四线程。
S1识别切片仅使用两个线程：服务后台线程兼任一次性操作执行者，另设接收解析线程；尚不承载多连接事件调度。

| 上下文 | 工作 | 限制 |
|---|---|---|
| 网络服务线程 | 状态机、请求处理、调度、重连计时 | 不阻塞等待模组命令结果 |
| 模组操作线程 | 消费操作请求，执行上电或AT事务，报告结果 | 不决定平台和业务重试策略 |
| 接收解析线程 | 持续解析响应、URC、定长载荷，唤醒事务或投递事件 | 不在回调内同步发起阻塞AT操作 |
| UART回调／中断 | 搬运少量数据、记录硬件错误、通知解析 | 不组平台报文、不写Flash、不等待AT结果 |

AT组件中的完成通知可以直接唤醒模组操作线程；服务层再通过结果事件更新状态。
关键完成／复位事件必须有预留容量或明确的可恢复通知机制，不能队列满就静默丢弃。
通知可以合并时必须证明不丢状态，不能任意覆盖一条有顺序意义的事件。

当前 `app/gt02_app.c` 仍执行IMU轮询和LED心跳。后续接入时只装配和启动网络服务，
不要把模组启动等待、TCP连接等待放进该循环，也不把它们放进公共系统工作队列长期阻塞。

## 8. 缓存：独立数据归属，共享底层传输

```text
接收：UART公共缓存 → 解析连接编号及载荷 → 对应连接RX缓存 → 对应上层协议
发送：各连接TX队列 → 公共调度器 → 一个AT事务执行器 → UART
```

### 8.1 每条连接的TX和RX

第一版采用静态、有界资源，每路独立设置容量，不要求四路容量相同。
TX保存有长度、请求编号、会话信息的数据块；RX提供有序字节流或有明确生命周期的分块。
RX数据块边界只是内部传递边界，不充当产品报文边界。

设计默认：上层发送时整笔复制入队，空间不足整笔拒绝，不悄悄接收一半。
已接收请求必须得到完成、失败或取消结果。以后若采用零拷贝，必须重新定义缓冲所有权契约。
接收接口优先将数据复制给调用者；解析器内部临时指针不能在回调结束后继续引用。

独立队列不强制物理内存完全分离。未来使用公共块池时，仍要有每连接配额、总上限及关键资源预留。
原始接收缓存、载荷缓存和事件队列不能在每个边界机械再复制一次，应按生命周期设计数据流。

### 8.2 Lierda定长载荷

根据旧实现，先解析URC中的连接编号和长度，再消费指定数量的原始字节，之后恢复AT文本模式。
载荷可分多次UART到达，也可能和下一条响应同批到达；必须支持长度驱动的分段处理。
不能把载荷中的 `\0`、换行、`OK` 或类似URC的字节当作控制信息。

长载荷可增量交付，不要求整条URC载荷一次放进一个巨大临时数组；具体上限及通知格式以实物手册和抓包为准。
缓存满、长度非法或接收超时后，要定义如何消费剩余载荷或重新同步，再恢复文本解析。
只关闭某条TCP不一定修复已经错位的公共串口流。

### 8.3 不照搬BG9x的缓冲假设

本机 `quectel-bg9x.c` 使用“数据就绪URC通知，再由 `QIRD` 按需读取”的路径，
并不为每个socket建立常驻完整RX/TX FIFO。旧Lierda路径则直接接收推送载荷，两者不同。
如果后续确认实际型号支持合适的被动读取模式，可以另做取舍记录，不能仅因命令名称相似就切换。

## 9. 多连接调度与AT串行化

连接内保持FIFO顺序；连接间先实现轮转，再根据产品需要加入可配置权重和防饿死规则。
发送权重不等于Zephyr线程优先级，也不等于TCP/IP网络侧的QoS承诺。

- 每次只向模组执行器提交一个受控操作，适配内部同时只允许一个UART AT事务拥有发送权。
- 一次“命令、提示符、载荷、发送结果”作为受保护过程，不允许其他连接的命令穿插载荷。
- 高优先级任务只能在允许的事务边界获得调度，不能强行抢占已经开始的载荷发送。
- 大数据在模组允许的发送边界分块，调用者不必自行理解AT最大长度。
- 分块中途失败时，已发字节与剩余字节分开记录，不把整笔数据无条件从头再发。
- 事务有截止时间，等待执行器和锁的时间也计入评估，不能只限制等待 `SEND OK` 的时间。
- 数据任务与连接、关闭、状态查询等控制任务都进入统一受控流程，不能暗中绕过调度写UART。

连接命令被接受后，若模组允许其他操作继续，可记录待完成连接，由连接编号对应的URC结束操作。
不要持有公共事务锁等待长达数十秒的远端连接结果，导致已在线链路无法发送。
若实际模组限制这种并行，则明确限制、采用有界超时并测量影响，不虚构并发能力。

## 10. 接口契约与完成语义

下面是规划中的能力，不是已经创建的头文件或可直接编译的API。

| 对外能力 | 约定 |
|---|---|
| 启动／停止网络服务 | 异步组织公共资源；停止时处理所有连接及未完成请求 |
| 配置／启停逻辑连接 | 使用逻辑通道，不暴露模组socket编号；目标地址作为参数或配置传入 |
| 发送数据 | 校验后整笔复制入队；返回成功只表示接受请求，异步事件携带最终结果 |
| 读取数据 | 只读取指定逻辑连接，返回实际字节数；空缓存与连接失效要能区分 |
| 查询状态 | 提供一致快照，不返回可随意改写的内部全局结构 |
| 结果与状态事件 | 带通道、请求编号、会话信息及错误；公共网络故障有明确作用范围 |

模组接口表达“查询注册、配置APN、激活数据连接、连接、发送、关闭”等小能力；
Lierda文件才包含具体AT字符串。业务不提供一个能绕过所有权的通用“随便发AT”后门。

必须区分三级结果：

1. **入队成功**：网络服务接受并保存了请求。
2. **模组发送结果**：适配层确认到模组报告的结果，不等于平台业务已处理。
3. **平台应答成功**：对应协议验证到匹配应答，由上层判定。

超时可能表示结果未知，而不一定是一个字节都没发出去。断线后是否重发、重放是否合法及如何去重由上层协议决定。
新TCP会话不自动接着发送旧会话某条报文的后半段；旧请求需要明确完成、失败或取消处理。

## 11. 一次报警发送与接收的完整过程

1. 业务判定报警，协议模块生成报文，并选择已配置的逻辑通道。
2. 网络服务复制报文入该路TX队列，返回入队结果。
3. 调度器在该路在线且资源允许时选择其队首任务。
4. 适配层映射模组编号，执行Lierda发送事务，等待结果；接收解析同时持续运行。
5. 操作结果交给服务，服务更新统计并通知请求方，不把模组结果当作平台应答。
6. 平台数据到达时，适配层按URC编号与长度提取载荷，交付该连接RX入口。
7. 上层协议从字节流组包并校验应答；业务结束报警会话或安排后续动作。

## 12. 异常、恢复与低功耗边界

| 情况 | 处理方向 |
|---|---|
| 单路服务器拒绝或关闭 | 该路失败／断开，有限退避；不默认重启整个模组 |
| 无SIM、注册失败、无信号 | 公共状态不可用，限次或限时重试后退避；保留其他产品功能 |
| 数据连接失效／模组重启 | 使相关连接、映射及未完成事务失效，先恢复公共依赖 |
| 单路TX队列满 | 明确拒绝新请求，由调用者决定延后或丢弃 |
| 单路RX缓存满 | 报告数据不完整，不静默丢字节；按策略使该连接失效或恢复 |
| UART溢出／解析失步 | 公共传输故障；停止把数据当有效载荷，执行有界重同步或恢复 |
| AT超时／迟到响应 | 结束当前事务并处理不确定状态；避免把迟到结果交给下一次请求 |
| 正常关机／产品休眠 | 上层协调全部连接需求，服务组织停止，适配按型号执行关机及引脚状态处理 |

重试必须有次数或时间预算、退避和升级条件，不能在多层各自无限重试。
正常关机与故障强制断电分开定义，不能把每次失败都处理成直接切断模组电源。
本阶段不承诺具体待机电流；DTR、RI等未确认接线不得被假定可用于休眠或唤醒。

## 13. 文件与配置归属

以下为组件归属。S1已加入模组接口、服务和两部分适配；其余能力按切片创建，不预建空模块：

```text
app/gt02_app.c                         装配与启动
services/network/gt02_network_service.* 连接管理、缓存、调度
interfaces/gt02_modem.h                通用模组能力和事件契约
adapters/modem/gt02_modem_zephyr.*      UART、GPIO、硬件时序
adapters/modem/gt02_modem_lierda.*      型号命令、响应和载荷处理
adapters/modem/                        按需加入AT组件封装，不新造通用解析引擎
lib/                                  对应产品协议出现时再加入
```

- DTS／pinctrl：UART和GPIO拓扑。当前私有接口节点只描述接线，不自动创建设备驱动或上电。
- Kconfig：4G能力、最多连接数、缓存容量、栈预算等编译选项。可规划 `CONFIG_GT02_MODEM_MAX_CONNECTIONS=4`，但目前尚未声明该选项。
- `prj.conf`：选择实际需要的UART、AT组件及项目功能；不因本设计自动启用PPP或所有Modem驱动。
- CMake：按功能选择已经实现的源文件，不把运行策略写进构建脚本。
- 运行时配置：连接目标、APN和产品可调整策略；敏感信息不写进公开日志。

AT机制优先复用Zephyr已有组件。针对旧Lierda定长推送格式，优先验证 `modem_cmd_handler` 的适用性；
它位于SDK驱动内部目录，有版本耦合，相关引用必须封闭在适配部分，不修改SDK源码。
公开的 `modem_chat` 也是候选，但须先验证提示符、URC和二进制载荷边界，不能仅凭文本匹配示例就决定覆盖全部收发。

## 14. 资源预算、日志与可观测性

不沿用“每路随意分配一个大数组”的做法。实现前明确每连接TX/RX容量、块数、控制队列深度、
UART峰值缓存、解析缓冲、AT最长响应、事务截止时间及三个执行上下文的栈预算。

新增RAM至少核算：各路TX与RX容量之和、队列与连接元数据、公共接收／解析缓冲、线程栈和同步对象。
若共享内存池，则按实际池容量计入，不再重复计算其逻辑配额；还要计入对齐及框架开销。
本设计没有实测数值，不能据此声称RAM或时延已经满足产品要求。

日志记录通道、请求编号、会话、状态变化、错误原因、重试次数和队列高水位。
测试记录各路吞吐、排队时延、最坏事务耗时、RX/TX溢出及线程栈高水位。
禁止默认打印SIM完整标识、APN密码、认证凭证或全部平台载荷。

## 15. 按阶段实施和验收

本表为验收计划；S1已有代码和构建检查，但仍待实板验收，不能把本表当成通过记录。

| 阶段 | 实现重点 | 验收重点 |
|---|---|---|
| S0 型号与契约 | 确认型号／固件／4连接能力、时序、数据格式及资源限制 | 明确手册与旧行为差异；没有依据的参数不硬编码 |
| S1 上电识别 | UART、控制GPIO、AT响应和基础URC | 有界失败；调试和脱机冷启动都能得到正确结果；IMU不被阻塞 |
| S1.5 状态查询 | 同一服务线程中查询CPIN/CSQ/旧CGREG，无APN/PDP/TCP | 数据行与最终结果区分；未知、无卡、锁卡、拒绝与限时等待不混淆 |
| S2 单路TCP | 建立、发送、接收、关闭 | 固定数据回显；二进制与分片完整；三种完成语义分开 |
| S3 四路与调度 | 四对象、独立缓存、公共调度 | 四路同时在线不串数据；单路大流量不长期饿死其他路 |
| S4 故障恢复 | 断线、公共掉网、复位、超时与资源耗尽 | 单路与公共故障范围正确；迟到结果不误关联；资源能回收 |
| S5 产品协议 | 报警、定位等逐项接入 | 旧业务行为对齐；应答匹配、断线重发与去重规则明确 |

解析器测试使用抓包或构造输入，覆盖逐字节分片、多条同批、响应与URC交错、非法编号／长度、
载荷包含AT关键词、超长与接收中断。四路测试分别使用可区分的数据，确认路由、字节顺序和长度。
再模拟某路停读、TX/RX队列满、连接迟迟无结果、服务器断开、模组重启和公共UART异常。
最终进行持续压力与独立冷启动测试，记录RAM、栈、调度延迟和IMU采样质量，不能只看“连接成功”。

## 16. 实施前还需确定什么？

1. 实物完整型号、AT版本以及是否支持所需的4路同时在线和操作并行。
2. POWER/PWRKEY时序、MCU侧极性、UART电平与未供电模组引脚的处理方式。
3. 每条逻辑连接的真实用途、独立启停条件、是否确实需要不同权重。
4. 最大产品报文、峰值与持续吞吐、允许排队时延以及RX消费者处理速度。
5. 每连接缓存和总RAM预算、模组内部缓冲限制以及可用流控条件。
6. APN、测试服务器、主动推送／被动读取的准确模式及发送结果含义。
7. 平台应答、重传、去重以及跨TCP会话的数据保留规则。

这些问题不阻碍先建立小接口和模拟测试，但会影响硬件时序、缓存容量、最终AT机制和产品承诺。

## 17. 后续评审的简明检查表

- 改模组只触及适配和硬件描述，网络服务不出现型号命令。
- 四路数据归属独立，公共UART与AT事务只有受控执行入口。
- 每份状态、每块缓冲和每个请求都有明确所有者及生命周期。
- 接收解析不被同步发送阻塞，服务状态机不被长AT等待阻塞。
- 超时、队列满、断线和重启均有结果，不静默丢请求或把旧数据当新数据。
- 优先级有边界和防饿死规则，不承诺能够打断在途AT事务。
- 设计、代码实现、构建结果和实板验证分开记录。
