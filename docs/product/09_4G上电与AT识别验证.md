## 1. 本轮实际调用关系

```text
app/gt02_app.c
    │ 非阻塞start，不等待AT
    ▼
network_thread：初始化 → 上电 → AT/ATE0 → ATI → 成功或失败后结束
    │ 同步调用能力接口                      ▲ AT完成通知
    ▼                                      │
Lierda适配：复用SDK modem_cmd_handler    modem_rx_thread
    │                                      ▲ 持续解析响应和基础URC
    ▼                                      │
硬件适配：GPIO上电、延迟初始化UART1、公共接收环形缓存
                                           ▲ UART接收中断搬运
```

S1只有两个新增线程。服务线程暂时兼任一次性操作执行者，不承载四连接事件调度。
后续实现多连接时再按[专项设计](../设计文档/4G多连接分层架构设计.md)分离服务调度与模组执行器。

## 2. 文件职责

| 文件 | 本轮职责 |
|---|---|
| `interfaces/gt02_modem.h` | 普通C能力契约和有界ATI文本；无Zephyr、GPIO或UART类型 |
| `services/network/gt02_network_service.c/.h` | 非阻塞启动、S1流程、状态快照、打印型号与失败原因 |
| `adapters/modem/gt02_modem_lierda.c` | SDK解析器配置、接收线程、AT/ATE0/ATI事务和基础URC |
| `adapters/modem/gt02_modem_zephyr.c/.h` | DTS资源获取、旧板电源时序、UART接收缓存、错误锁存 |
| `app/gt02_app.c` | 初始化原有外设后启动服务，继续IMU轮询和LED心跳 |

SDK内部头文件目录只加给两个modem适配源文件。没有复制SDK解析器，也没有修改SDK源码。
UART传输适配使用Zephyr中断接口，并显式检查缓存溢出、硬件错误和过长文本；这不是另一套AT解析引擎。

## 3. 硬件与启动时序

从 `modem0` 节点取得UART及控制GPIO，不在C文件中重复写物理引脚。
实际接线仍为UART1，MCU TX=P0.27、RX=P0.07；POWER=P0.31、PWRKEY=P1.08；115200、8N1、无流控。

UART1现在为 `status = "okay"`，同时设置 `zephyr,deferred-init`：
**有可引用的设备实例，但不在main之前初始化UART；仅在电源时序完成后调用 `device_init()`。**
关闭S1开关时没有应用调用该初始化，因此不会自动通过此UART发送AT或配置模组控制GPIO。

电源时序取自旧 `appcom/netmod/netmod_port_lte.c` 的非 `PRODUCT_GT06` 路径：

| 顺序 | MCU侧逻辑操作 | 后续等待 |
|---|---|---|
| 1 | 初始化POWER=0、PWRKEY=0 | 100 ms |
| 2 | PWRKEY=1 | 100 ms |
| 3 | POWER=1 | 100 ms |
| 4 | PWRKEY=0 | 1000 ms |
| 5 | PWRKEY=1 | 200 ms |
| 6 | 初始化UART1并启动接收解析 | 默认5000 ms测试等待 |
| 7 | 单次依序发送AT、ATE0、ATI | 每条独立等待，默认3000 ms超时 |

逻辑电平通过GPIO flags映射。MCU侧高有效不等于裸模组PWRKEY高有效，不能忽略板上反相电路。
100/1000/200 ms是旧板参考行为；5000 ms是可调测试等待预算，不是已确认的所有Lierda型号启动参数。
这轮按用户指定的旧工程行为实现，仍需根据ATI结果核对实际型号和固件。

## 4. 开关与资源参数

`prj.conf` 显式启用基础能力：

```ini
CONFIG_MODEM=y
CONFIG_MODEM_CONTEXT=y
CONFIG_MODEM_CMD_HANDLER=y
CONFIG_UART_INTERRUPT_DRIVEN=y
CONFIG_RING_BUFFER=y
CONFIG_GT02_MODEM_BRINGUP=y
```

项目Kconfig中的S1开关依赖上述能力，不反向select整个MODEM菜单，避免依赖环。
SDK会提示 `Experimental symbol MODEM_CONTEXT is enabled`；这是已知实验性内部API依赖，不是被屏蔽的构建错误。
未启用 `MODEM_CELLULAR`、`MODEM_QUECTEL_BG9X`、`MODEM_SOCKET` 或PPP。

| 项目选项 | 初始默认值 | 含义 |
|---|---|---|
| `GT02_MODEM_BOOT_WAIT_MS` | 5000 | UART启动后到第一次AT的等待预算 |
| `GT02_MODEM_AT_TIMEOUT_MS` | 3000 | 每条命令等待结果的上限；无自动重发 |
| `GT02_MODEM_UART_RX_SIZE` | 2048 | 公共原始UART缓存，不是每连接TCP缓存 |
| `GT02_MODEM_RX_STACK_SIZE` | 2048 | 接收解析线程栈，尚无实板高水位记录 |
| `GT02_NETWORK_STACK_SIZE` | 2048 | S1服务后台线程栈，尚无实板高水位记录 |

此外，SDK解析池为8块256字节，单行最多255字节，ATI总快照384字节，包含换行和结尾NUL。
超出上限返回错误，不截断后宣称识别成功；两个栈大小只是首轮预算，并非已经验证的最小安全值。

关闭测试：把 `CONFIG_GT02_MODEM_BRINGUP=n`，重新构建并烧录。
这样不编译三个服务／适配源文件，也不启动线程或执行电源时序；基础库配置仍可保留。
如需彻底移除UART设备实例和相关资源，还要结合其他使用者调整DTS及公共配置，不能把“停止S1”当成完整产品电源管理。

## 5. 状态和错误语义

```text
IDLE → INITIALIZING → POWERING_ON → HANDSHAKING → IDENTIFYING → MODEM_IDENTIFIED
                       任一步失败 ───────────────────────────────→ FAILED
```

- `gt02_network_service_start()`：只启动后台流程，返回0不表示模组已经识别；重复调用返回 `-EALREADY`。
- `gt02_network_service_get_status()`：在线程中读取一致快照；不能在ISR调用。
- 模组生命周期接口只由一个后台线程拥有，不承诺可由任意线程同时调用；命令操作另有非阻塞互斥保护。
- 识别检查与旧工程一致，ATI文本包含 `Lierda`（另接受小写）才通过，不预设具体型号。未匹配时先打印原文，再报告失败。
- READY类启动URC只作为启动信息，不能替AT释放成功信号。握手后再次出现RDY会保守地锁存复位错误。
- 正常关机通知、UART错误／溢出、过长文本或不支持的TCP推送都会终止本轮。
- AT超时后不再发下一条，避免迟到OK被后续事务误用；失败后需检查原因并重启设备，不支持直接重入测试。

失败会停止后续AT和接收，不自动反复上电，也不强制切断模组电源。
这不是正常关机实现；失败后模组可能仍耗电。需要断电结束测试时，由用户按板卡正常操作执行。
成功后接收线程继续等待基础URC；复位等错误可由驱动日志及状态快照观察，但没有自动恢复逻辑。

## 6. 如何在板上验证？

1. 确认使用NCS工程 `MyProject`，按旧板硬件正常供电并接好UART0日志。保持当前IMU、Flash验证接线，不为测试临时复用它们的引脚。
2. 执行 `NCS: Build GT02` 或 `scripts/ncs.ps1 -Action Build`，确认本轮固件构建成功。
3. 用户自行执行已有烧录任务；本轮代码实现过程不自动烧录。
4. 从断电重启开始保留完整UART0日志；LED心跳和IMU日志应继续出现。
5. 模组完成启动等待后，应看到AT、ATE0、ATI的发送日志。记录真实ATI文本，核对型号和版本。
6. 成功时应出现 `S1 PASS: Lierda identified; network registration and TCP NOT tested`。
7. 再用独立供电、断开J-Link的冷启动方式复测；不能只凭调试器下成功判断脱机启动正常。

示意日志，不是本轮已经采集的实板结果：

```text
gt02_network: S1 begin: power-on -> AT -> ATE0 -> ATI (no SIM/APN/TCP)
gt02_modem: Power-on: legacy GT02 non-GT06 sequence; exact model pending ATI
... IMU和LED日志继续 ...
gt02_modem: TX: AT
gt02_modem: TX: ATE0
gt02_modem: AT handshake passed; echo disabled
gt02_modem: TX: ATI
gt02_network: ATI response:
<模组返回的真实厂商、型号、版本文本>
gt02_network: S1 PASS: Lierda identified; network registration and TCP NOT tested
```

如果只见 `TX: AT` 然后失败，优先核对电源时序、供电、UART方向、共同地、电平、115200设置及启动等待预算。
不要因失败盲目无限加延时或重启。先确认上电波形和是否有任何接收字节，再依据实际型号调整。
如出现Fault，保留本轮ELF和完整日志；不能用旧构建的地址符号解释新固件。

### 6.1 原始RX日志（2026-10-23新增）

当前 `prj.conf` 开启 `CONFIG_GT02_MODEM_RAW_RX_LOG=y`，并将全局日志缓冲设为
`CONFIG_LOG_BUFFER_SIZE=4096`，用于容纳启动阶段的突发输出。
调试结束可将前者改为 `n`；日志缓冲大小可另行恢复原预算。

日志位于 `gt02_modem_zephyr.c` 的 `iface_read()`：接收解析线程从环形缓存取到字节后，
先打印，再原样交给SDK AT处理器。没有在UART中断打印，没有新增解析器或改变匹配规则。
按用户要求，字符串日志改为按完整文本行输出，而不是按每次UART读取的分片输出。
接收线程使用256字节独立行缓存，跨 `iface_read()` 调用累积；遇到CR或LF后，
对非空行打印一次 `gt02_modem_uart: RX raw: <完整文本行>`。
CRLF只产生一条日志，空行不打印，不过滤未匹配的非空响应或URC。
例如即使 `RDY` 的三个字符分三次收到，也只在行结束后显示 `RX raw: RDY`。
该缓存不修改原始接收数据；补NUL后按字符串打印，延迟日志会复制文本，随后可复用缓存。
每行最多255字节，日志副本超长时在行结束标注 `[truncated]`，不把截断当完整行；
当前S1的UART检查本身仍会在超长行时先锁存错误并停止接收。
没有行结束符的片段暂不打印，停止接收时未完成行也不冒充完整行；没有增加空闲超时猜测边界。
这里的“完整”指一条CR/LF分隔的文本行，不是整次AT事务：ATI仍按厂商、型号、版本、OK分别显示，
已有服务层ATI汇总日志继续保留。将来无换行的发送提示符和二进制数据需另行支持。
此方式仅用于当前S1的AT文本，未来二进制载荷中的NUL及不可见字节不能靠字符串完整展示。

此日志只覆盖UART已启动、接收未停止、且成功读出环形缓存的数据，不能追溯启动UART前的内容。
当前S1仍会在硬件错误、缓存溢出、NUL或过长文本等情况停止，不能视为无条件串口抓包器。
延迟日志使用有限缓冲，持续大流量时可能丢日志或拖慢消费；4096字节也不保证无丢失。
正式产品默认应关闭原始日志，以减少开销并避免泄露后续SIM身份、认证或业务数据。

上一次十六进制日志版本的本地构建已通过（2026-10-23，NCS 3.4.1，原 `build_ncs_341`）：
Flash 56128 B、RAM 25088 B；已核对RX开关启用、日志缓冲4096字节、Flash破坏性自测仍关闭。
本次未自动烧录，尚未实板核对原始字节输出及日志丢失情况；下文第8节保留的是接入S1时的历史构建记录。

随后按用户要求改为字符串输出，构建也已通过：Flash 56148 B、RAM 25088 B。
原RX开关和日志缓冲配置不变；本次仅完成软件构建验证，未烧录或实板验证。

用户回传的字符串版日志出现 `R`、`D`、`Y` 各一条，说明UART逐字符分片触发了日志，
不是模组主动把URC拆成多条。本次加入跨批次行缓存后的构建已通过：Flash 56220 B、RAM 25344 B。
尚未烧录或做输入注入；复测时应确认逐字符到达的 `RDY\r\n` 只打印一条 `RX raw: RDY`，
同批多行各打印一条，CR和LF分两批到达也不重复，ATI多行和最终OK均可见。

## 7. 主要失败路径的验收清单

- 模组不响应：单次命令超时，服务报告失败，IMU／LED继续；不自动重发和反复上电。
- ATI为空、过长或厂商不符：不能报PASS，保留可用诊断；过长内容不会当成完整身份。
- UART硬件错误／接收缓存满：锁存错误并停止，不能静默丢字节后继续识别。
- 响应分片、多行ATI、启动URC插入：SDK解析器与本地捕获逻辑应正确协作。
- 握手后模组复位／意外TCP推送：终止S1，不把后续未知载荷当作型号文本。
- 重复start：返回 `-EALREADY`，不产生第二套线程或再次电源脉冲。
- 开关关闭：构建通过，无S1应用调用和线程；UART1仍保持延迟初始化。

本轮未在真实硬件执行上述路径，也未做协议输入注入测试；这些条目是实板／后续测试夹具的验收要求。
