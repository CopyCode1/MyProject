# 4G重建第一步：硬件适配

日期：2026-10-29。用户确认仅重建4G，保留其他外设。

## 当前程序做什么

硬件装配先调用 `gt02_modem_hw_init()`，将POWER和PWRKEY配置为未激活。
**当前临时开启`CONFIG_GT02_MODEM_HW_TEST=y`**，随后启动上下电测试及唯一RX打印线程。
测试自动执行首次上电，每10秒发起一次硬件下电/重新上电，不发送AT或接入网络服务。
初始化日志为：

```text
4G hardware prepared: supply inactive, UART not started; no AT/network
```

这条日志只表示GPIO准备成功，不代表4G供电、通信或网络通过。
IMU、Flash和LED的原有调用及配置保留；已有IMU轮询注释没有恢复，Flash擦写自测仍关闭。

关闭临时测试开关后，启动行为恢复为只准备控制脚，不给模组上电、不启动UART或创建测试线程。

## 对外只提供五个入口

| 接口 | 意义 |
|---|---|
| `gt02_modem_hw_init()` | 准备控制脚；重复调用不改变现有状态 |
| `gt02_modem_hw_power_on()` | 先启动UART接收，再执行旧板供电/PWRKEY步骤，不等待AT或网络 |
| `gt02_modem_hw_power_off()` | 先切电，再挂起UART、清缓存并释放PWRKEY；不代替模组正常关机 |
| `gt02_modem_hw_read(..., timeout)` | 等待并复制原始字节；K_NO_WAIT轮询，有限超时或K_FOREVER等待 |
| `gt02_modem_hw_write()` | 同步提交指定长度的字节，返回实际提交数量 |

UART启停、PWRKEY/供电脚操作、等待和错误检查不再是对外入口，故障通过读写/上下电返回值报告。
不为封装额外建立空层或函数转发文件；后续出现真实型号差异或业务需求时再拆分、扩展。

```text
UART中断 → 原始RX缓存 → 后续的唯一解析者
后续执行者 → write → UART
生命周期调用者 → power_on/power_off → 内部GPIO/PWRKEY/UART动作
```

NUL、CR/LF、`OK`及其他二进制字节都不在此层解释，也不打印原始文本。
有效接收窗口内的容量不足或UART错误会锁存故障并停收，禁止静默覆盖；成功开启新的接收周期才清除故障。
尚未开始供电时的输入按下文“供电前帧错误修复”单独处理，不混入本轮有效URC。
控制操作与单次写互斥，RX复制单独用短自旋锁，不因长TX而等待控制锁。
这不是AT事务调度器；多个write组成的协议阶段仍要由未来AT层管理。

## 临时10秒上下电与URC打印

测试位于[测试源码](../../tests/bringup/gt02_modem_hw_test.c)及[唯一启动入口](../../tests/bringup/gt02_modem_hw_test.h)，
由`CONFIG_GT02_MODEM_HW_TEST`选择编译；硬件五接口不增加日志或测试入口。

- 两个测试线程各预留2048字节栈；电源线程执行会阻塞的上下电，RX线程从首次UART启用起持续读取。
- 首次上电成功后等待10秒，发起第一次下电/上电；以后以10秒为正常重启发起间隔，包含约2秒下电及1.5秒上电步骤。
- 若一次操作耗时超过周期，不立即追赶补发重启，而是从完成时重新等待10秒。
- 原始RX跨UART读取批次拼成完整CR/LF文本行，不逐字符打印；空行省略。
- 超过256字符的日志副本明确标注`[part]`/`[last part]`；非可打印字节显示为`\xNN`，不会被NUL截断。
- 主动切电时，未完成的旧文本标注`[partial]`，不能和下一次启动的内容拼接。硬件断电边界允许丢弃尚未处理的旧数据。
- 上下电失败立即停止循环；在线RX故障会记录并在下一次定时动作前停止，最迟约10秒，不做自动恢复。
- 这是启动URC等小流量调试显示，仍受硬件RX缓存、调度和日志缓冲容量限制，不承诺无限流量零丢失。

预期日志示例（实际URC由模组决定，可能早于power_on结果日志）：

```text
4G initial power_on begin
4G RX: RDY
4G initial power_on result=0
4G cycle=1 power_off begin
4G cycle=1 power_off result=0
4G cycle=1 power_on begin
4G RX: RDY
4G cycle=1 power_on result=0
```

返回0仅表示硬件接口完成；是否观察到每次启动URC由实板日志确认。
没有发送AT，因此本测试没有验证write、AT应答、注册或TCP。
验证后设置`CONFIG_GT02_MODEM_HW_TEST=n`并重新构建/烧录，即移除两个测试线程和原始RX日志，恢复仅初始化。

### 首次上电返回-5的诊断（2026-10-30）

用户实板日志显示：0.299秒开始上电，1.800秒返回`-5`并停止测试。
`-5`是`-EIO`。约1.5秒耗时与当前板级电源步骤一致，优先怀疑UART在此期间已经锁存错误，
最后的`io_status()`才将错误返回；仅凭原日志不能确定是UART、GPIO还是驱动初始化失败。

首先增加了失败来源与首次UART错误快照，原诊断版本保持原有时序、五接口及遇错停收策略：

```text
UART RX fault: at=... ms, stage=before_supply, flags=0x..
UART flags: overrun=... parity=... framing=... break=...
power_on failed: RX/transport error=-5 after power sequence
```

上面为诊断输出格式。随后用户实板确认首次错误为`at=255 ms, stage=before_supply, flags=0x04`，
即模组供电使能之前出现framing，软件将它锁存成-EIO、停收，约1.5秒的上电步骤结束后返回失败。
这确认了软件停机的直接路径，不能据此断言RX实际电压或板上哪一处电气因素造成了帧错误。

| 字段 | 解释 |
|---|---|
| `before_supply` | 模组供电使能之前，UART已启用接收 |
| `supply_enable` | 使能供电及其后100 ms等待阶段 |
| `pwrkey_start` | 供电后的启动按键时序 |
| `active` / `power_cut` | 上电接口成功后 / 主动切电阶段 |
| `flags`含`0x01` | UART硬件overrun，不能与软件RX环形缓存不足混为一谈 |
| `flags`含`0x02` | parity错误 |
| `flags`含`0x04` | framing错误，例如停止位不符合预期；具体电气/配置原因仍需查证 |
| `flags`含`0x08` | break，RX低电平保持时间达到硬件判定条件 |

本机nRF UART驱动的`uart_err_check()`读取会清除错误源，因此ISR只读一次并保存原始标志。
ISR仅保存快照和停收，线程在释放自旋锁后打印，每个接收周期最多打印一次详细UART故障。
该诊断版本没有忽略framing/break，也未在启动后清空错误继续运行。
若阶段在供电前或启动切换期间且存在framing/break，才进一步核对RX实测电平、接口电平及供电转换；
若错误源实际是GPIO/初始化，按新增的对应失败来源定位。

2026-10-30诊断版本构建通过：Flash 54,500 B、RAM 21,760 B。随后实板结果确认了供电前帧错误导致停收的路径；修复见下节。

### 供电前帧错误修复（2026-10-30）

依据上述实板证据，保留“先开UART再上电”的顺序，调整未供电阶段的接收规则：

- 仅在`uart_start`和`before_supply`阶段，将纯framing/break计为未供电输入，不锁存为本轮传输故障，不停收。
- 仍读取UART FIFO，让本机驱动清除接收完成事件并推进下一次接收；未供电输入不进入软件RX缓存。
- `overrun`、`parity`、负API错误，以及混有其他错误位的情况不适用上述规则，继续按故障处理。
- 从进入`supply_enable`阶段起，即使模组还未输出RDY，也恢复严格错误检查及原始字节缓存。
- 供电步骤结束后不会清掉已收到的有效URC或供电后的故障；从未把所有启动期错误一概忽略。
- 在电源线程汇总一次计数，例如`UART pre-supply input discarded: line_errors=... flags=0x04 bytes=...`，不在ISR刷日志。

实际判定函数与本机SDK的UART错误枚举已通过16个编译期边界用例，包含供电前/供电后、混合错误和负错误码；
还验证了故意给出错误预期时编译器确实拒绝通过。此检查只覆盖纯分类逻辑，不是UART中断或实板时序模拟。
修复版本NCS构建通过：Flash 54,776 B、RAM 21,824 B。已检查五接口不变、ISR不打印日志、供电后不清有效缓存，Flash适配源码未改变。
尚未烧录复测，不能承诺所有供电转换异常已经解决；应重新观察首次上电结果、启动URC及多轮10秒上下电日志。

## 配置和边界

- `CONFIG_GT02_MODEM_HW=y`：编译硬件底座并在应用中准备GPIO。
- `CONFIG_GT02_MODEM_HW_TEST=y`：当前临时自动上下电及URC日志验证；正式功能默认应关闭。
- `CONFIG_GT02_MODEM_UART_RX_SIZE=2048`：原始RX缓存容量。
- `CONFIG_PM_DEVICE=y`：让UART1显式挂起/恢复使用驱动的休眠引脚配置；不因此启用系统PM或运行时自动挂起。
- UART仍是DTS中的延迟初始化设备，只在显式power_on内部初始化。

`power_on()`先初始化/恢复UART并开启接收，再执行旧GT02非GT06启动步骤：初始等待100 ms、PWRKEY激活后100 ms、
供电使能后100 ms、PWRKEY释放后1000 ms、再次激活后200 ms。
缓存和旧通知只在本接收周期开始前清理，上电步骤结束后不再清理，保留早到的启动URC。
这些旧板适配步骤集中在内部函数，不能当成所有模组的通用时序；返回0也不代表收到RDY/OK。

`power_off()`按用户确认的当前板要求执行硬件切电：先关闭供电使能，随后立即挂起UART并把PWRKEY置未激活，
最后保留旧板2秒间隔；不会在切电与UART停机之间额外等待2秒。
它没有复刻旧工程1.5秒PWRKEY脉冲和12秒关机等待，也不发送关机AT。
正常关机须由后续型号后端完成协议/确认后，再调用硬件下电。不同板子的断电电气兼容性需要实测。

停止成功会丢弃RX缓存，因此调用者必须先结束/失效正在处理的协议。
下电会使本地接收代次失效，并唤醒旧read返回取消/未就绪错误；不等待消费者线程退出。
这只防止本地read跨接收周期，不解决线上没有标识的迟到AT回复。上层仍要管理消费者和协议生命周期。
切电失败时保留原供电记录，不继续关闭UART，锁存错误并唤醒read；调用者应处理失败或再次下电。
切电成功后，即使UART挂起失败也不能再把供电记录改回开启；锁存故障并禁止继续收发，再次下电可重试串口清理。
UART/PWRKEY同时清理失败时返回本次最先出现的错误；已有锁存错误不被后续清理错误覆盖。

read只等待至少有一些字节可读，不等待填满buffer，也不表示整条AT/业务报文已经收到。
K_NO_WAIT无数据返回0且received为0；有限等待无数据返回-EAGAIN；硬件错误、溢出和下电通过负错误码报告。
即使有旧信号量通知，有限等待也共用同一个截止时间，不会反复延长预算。

同步TX用于起步阶段，不提供接口级发送超时；`written`仅表示提交给UART的字节数。
驱动初始化失败、异常硬件等待和具体供电行为不能靠构建验证，仍需实板检查。
