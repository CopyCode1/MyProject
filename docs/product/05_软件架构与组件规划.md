## 1. 目标与边界

首版产品的外部行为与旧 `gt02_4g` 目标一致，允许按功能切片逐步完成。架构同时支持更换 SoC、PCB 引脚、IMU 和通信模组时，把改动限制在对应的板级描述与实现层。

本文件规划组件及依赖，不代表这些组件已经实现。旧工程提供行为、数据格式、时序和异常情况的证据，不直接决定 Zephyr 的任务结构。显示屏仍是待确认能力；外部 NOR Flash 已进入只读诊断阶段，尚未承担产品数据存储或OTA。

判断一个边界是否有效，用实际变更来检验：换引脚主要改 DTS/pinctrl；换 LSM6DSO 主要改 IMU 适配器及板级节点；改静止报警门槛只改产品策略或配置。若同一变化需要改动多个不相干组件，应重新检查接口。

## 2. 层级和依赖方向

```text
┌─────────────────────────────────────────────────────┐
│ app：装配、启动顺序、产品模式与状态机                  │
├─────────────────────────────────────────────────────┤
│ domain：纯 C 产品规则、状态转换、报警判定              │
├─────────────────────────────────────────────────────┤
│ services：IMU、输入、UI、电源、定位、网络、存储、OTA 等 │
├─────────────────────────────────────────────────────┤
│ interfaces：确有替换点时定义的小接口与公共数据类型     │
├─────────────────────────────────────────────────────┤
│ adapters：Zephyr Sensor/GPIO/UART/Flash、具体外设     │
├─────────────────────────────────────────────────────┤
│ Zephyr API 与驱动 ← board DTS、pinctrl、binding       │
└─────────────────────────────────────────────────────┘
```

实际硬件调用链是 `app → services → adapters → Zephyr`；`interfaces` 放跨边界的样本类型或必要的能力契约，不要求每次调用都经过独立的接口对象。`domain` 接收服务提供的普通 C 数据和显式时间，不包含 Zephyr、具体芯片或板级头文件。`app` 负责装配和调用；接口由实际使用者需要的能力驱动，不为每个底层 API 机械建立一层包装。

`lib` 放纯算法与协议编解码，如 NMEA、XRP、JT808 和运动判定。它可以被 `domain`、`services` 和 `adapters` 中适当的组件使用，但不得反过来访问设备、线程或全局产品状态。厂商代码如果必须保留，限于对应 `adapters` 内。

## 3. 建议目录与源文件归属

下表是目标归属，目录在对应切片开始时创建。当前工程已有的 `boards/`、`dts/`、`src/main.c` 保持有效。

| 路径 | 职责 | 首次创建时机 |
|---|---|---|
| `src/main.c` | 极薄入口；产品装配在 `app/` | 已收敛为调用 `gt02_app_run()` |
| `app/` | 组件启动顺序；后续承载产品模式和顶层状态机 | 已有 IMU 验证期入口；产品状态机待实现 |
| `domain/` | 不访问硬件的休眠、报警、上报等产品规则 | 第一条需要跨服务决策的切片 |
| `services/imu/` | 当前拥有同步采样和最近结果；后续承载采样调度、工作/待机模式、运动事件 | 已有最小可运行服务，S1 继续扩展 |
| `services/input/`、`services/ui/` | 按键动作识别、LED/马达反馈调度 | 输入与 UI 切片 |
| `services/power/` | 电池、充电、唤醒源与设备电源请求协调 | 电源切片 |
| `services/location/`、`services/network/`、`services/remote/` | 定位汇总、连接管理、服务器交互 | GNSS、4G 和协议切片 |
| `services/storage/`、`services/ota/` | 配置/记录持久化；镜像接收、校验和升级状态 | 存储与 OTA 切片 |
| `interfaces/` | 跨实现边界的稳定能力接口和数据类型 | 已有 IMU 样本类型；其余按需加入 |
| `adapters/` | Zephyr 设备访问、模组控制及物理协议适配 | 已有 IMU Sensor 适配器；其余按需加入 |
| `lib/` | 可在主机上测试的算法及协议编解码 | 对应纯逻辑出现时 |
| `tests/` | 纯逻辑、组件与板级验证用例 | 对应功能切片 |

每个组件优先有自己的 `.c`、公开 `.h` 和必要的私有头文件；CMake 只列已实现的源文件。不要创建空模块、万能 `common.h` 或包含全部服务的总头文件。

## 4. 组件契约与状态所有权

| 组件 | 输入 | 输出/公开能力 | 唯一拥有的可变状态 |
|---|---|---|---|
| `imu_adapter` | 模式设置和采样请求 | 带时间戳的六轴数据或明确错误 | Zephyr Sensor 设备访问和驱动配置 |
| `imu_service` | 产品请求的采样模式、适配器数据 | 运动/静止变化、采样质量与最近有效数据 | 采样调度、传感器健康和运动判定状态 |
| `input_service` | SOS GPIO 的原始状态和时间 | 单击、双击、长按等动作事件 | 消抖及动作识别状态 |
| `ui_service` | 产品反馈请求 | LED/马达的有界执行结果 | 灯效与马达调度状态 |
| `product_app` | 按键、运动、充电、连接和定时事件 | 产品模式及对各服务的请求 | 顶层产品模式和转换上下文 |
| `power_service` | 产品模式、电池/充电测量、设备电源请求 | 可执行的电源动作与唤醒信息 | 电源域状态和请求引用关系 |
| `location_service` | GNSS、UWB 和其他定位数据 | 定位快照、质量和结果事件 | 当前定位任务与有效结果 |
| `modem_service` / `network_service` | 上报请求、4G UART 接收和模组状态 | 注册、连接、发送结果 | 模组状态机与连接生命周期 |
| `remote_service` | 网络收发、产品事件 | 经校验的命令与编码报文 | 会话、重传与协议状态 |
| `storage_service` | 版本化配置、记录读写请求 | 受控读写结果 | 持久化数据格式和写入顺序 |
| `ota_service` | BLE/UART/4G 固件数据块 | 写入、验证、激活和确认结果 | 升级会话与镜像状态 |

表中的能力是组件边界，不是现在必须固定的函数签名。实现时先写明输入数据的单位、有效期、所有权和错误码，再定义最小公开接口。跨组件读取状态使用快照或事件；只有该状态的所有者能修改它。

### IMU 的首个接口示例

当前已定义与 LSM6DSO 无关的 `gt02_imu_sample`：单调时间戳、加速度（`mm/s²`）和角速度（`mrad/s`）；当前仍是传感器原始轴顺序，产品坐标系待核对。读取接口以返回码表示有效性，最近样本在读取失败时失效。这个时间戳是当前读取时间，不是传感器逐帧硬件时间戳；复刻旧算法不要求给 FIFO 中的每一帧添加时间戳。

**S1 的 IMU 实现按旧工程收敛为两部分，不要求每部分都占一个通用架构层：**

1. **采样部分**独占 LSM6DSO、设置量程和高/低采样档、排空 FIFO、将一批样本转换为统一单位；对应用提供最近有效样本，未来确实需要连续原始数据上传时再提供有界批量缓冲。4G 线程不得自行访问 Sensor/I²C。
2. **识别部分**只接收采样部分提供的加速度、角速度及单调时钟值，保持旧工程的动静与跌落判定规则，不包含 Zephyr/寄存器头文件。它输出状态变化和档位切换请求；采样部分执行档位切换。产品应用负责静止报警计时、远程标志、LED 等后续动作，不在识别逻辑中直接调用这些模块。

当前 `services/imu/` 与 `adapters/imu/` 只是验证阶段的文件组织。正式落地时可按上面两项合并/重命名，不为保持五层图而继续添加转调文件。

旧 `gt02_4g` 行为基线来自 `appcom/imu/imu_common.c`、`appcom/imu/LSM6DSO_port.c` 和 `applications/gt02_new/src/gt02new_newui_app.c`：

| 项目 | 旧实现中实际使用的行为 | 新实现的保持点 |
|---|---|---|
| 正常采样 | 加速度 ±2g、陀螺仪 ±1000 dps、ODR 104 Hz；传感器 FIFO；IMU 任务约每 100 ms 排空一次 | 先实现连续批量采样，不能用应用每秒读取一次代替 |
| 动静判定节奏 | 识别回调至少间隔 200 ms；用系统毫秒/秒时钟计时，未给每帧保存时间戳 | 算法接收当前单调时钟值，保持门控及秒计数语义 |
| 进入静止 | 三轴相邻判定值差的绝对值之和除以 3，结果 ≤ 15 mg 时按秒累加；计数 `> 35` 进入静止 | 保持阈值、严格大于号和不满足条件时清零；阈值单位须先换算一致 |
| 恢复运动 | 静止时上述差值 ≥ 12 mg，一次符合即解除静止；旧代码中连续次数条件被注释 | 不擅自加入新的防抖时间；在回放测试中暴露可能的抖动 |
| 低速档 | 进入静止后请求 `LOWEST`，关闭陀螺仪，设置 LSM6DSO 的低速寄存器档位；恢复时请求 104 Hz | 保持自动切换及关闭陀螺仪；实际低速输出率与功耗板测确认 |
| 跌落标志 | 开机超过 10 s 后，三轴加速度各自绝对值均 < 300 mg，连续两次通过 200 ms 门控时置位；应用处理后清除 | 保持一次性锁存/清除语义；这只是旧代码的近 0g 跌落条件，不等于已确认的人体跌倒 |
| 其他旧接口 | `falldown_thresh` 在上述判断中未使用；LSM6DSO 端口的步数读取固定返回 0 | 不把未生效配置或步数接口误写成已实现功能 |

这里的“功能一致”指相同输入序列产生相同动静和跌落事件，以及相同的档位请求和上层处理；不要求复制 FreeRTOS 任务、直接寄存器调用或旧文件目录。先做纯 C 回放测试，再进行板上 FIFO、档位切换、I²C 错误和功耗验证。

目前已关闭 Zephyr Sensor/LSM6DSO 驱动，由 `adapters/imu/gt02_imu_zephyr.c` 独占 `imu0` 的 Zephyr I²C 访问。上电验证 WHO_AM_I，限时软复位，工作档配置 ±2g/±1000 dps、104 Hz、连续 FIFO，应用约每 100 ms 排空 FIFO；低速档关闭陀螺仪并沿用旧工程的 1.6 Hz 加速度计和 12.5 Hz FIFO 批处理设置。FIFO 溢出时清空旧帧并返回错误，不把失效快照作为新数据。上述寄存器行为仅通过编译，仍需板上测量实际采样间隔、丢样、CPU/I²C 占用和功耗；尚未实现动静/跌落识别。

S1 当前验证代码已建立以下文件，并保持板上输出可用：

```text
src/main.c                         # 调用应用启动，不持有传感器状态
app/gt02_app.c                     # 装配 IMU 服务和验证期日志消费者
interfaces/gt02_imu.h              # 与具体芯片无关的样本类型与单位
services/imu/gt02_imu_service.c    # 有界批量排空、最近结果及其有效性
services/imu/gt02_imu_service.h    # 初始化、档位、轮询和最近结果接口
adapters/imu/gt02_imu_zephyr.c     # Zephyr I2C、LSM6DSO寄存器/FIFO、单位转换
adapters/imu/gt02_imu_zephyr.h     # 仅供 IMU 服务使用的适配接口
```

正式整理时，以 `imu/gt02_imu_sensor.c`（采样、档位、对外原始数据）和 `imu/gt02_imu_detect.c`（纯 C 识别）为目标归属，合并或移动当前验证文件，而不是在其外再套一组转调层；同一切片增加旧输入轨迹的回放测试，不预建空目录。

当前接口的 `init`、`set_mode` 和 `poll` 返回可检查的错误；`get_latest` 在尚无结果或最近读取失败时返回 `-EAGAIN`。每个样本的时间戳是排空 FIFO 时的 Zephyr 单调时间，不是芯片逐帧硬件时间戳。当前快照没有时间有效期参数，调用方不能把长时间未更新的快照当作实时值。后续识别部分在进入/退出静止时请求高低采样档，产品坐标系变换只做一次。

下一步先在板上验证 FIFO 数据与 100 ms 排空量，再验证高低档切换、I²C 故障和功耗；之后用旧工程轨迹建立纯 C 动静/跌落算法回放测试。编译通过不等于板上行为已确认。

## 5. 事件、执行上下文与线程预算

跨服务事件从具体场景出发定义，例如 `KEY_ACTION`、`MOTION_CHANGED`、`CHARGE_CHANGED`、`POSITION_READY`、`MODEM_STATE_CHANGED` 和 `OTA_STATE_CHANGED`。事件载荷按值拷贝，并带单调时间戳；大数据通过有明确生命周期的缓冲区传递。产品状态机只消费已校验的事件，不直接在 GPIO/UART 回调里运行。

| 执行位置 | 负责工作 | 约束 |
|---|---|---|
| `main` / 产品控制上下文 | 启动顺序、顶层事件处理和状态转换 | 不承载 104 Hz 采样或长时间阻塞的 AT 操作 |
| GPIO、UART、BLE 回调 | 搬运最小数据或投递事件 | 不阻塞、不解析长报文、不写 Flash |
| IMU 采样上下文 | 调用可能阻塞的 Sensor/I²C API，计算样本有效性 | 正式高频采样阶段使用独立线程或专用工作队列；先测量实际耗时与栈 |
| 4G/GNSS 处理上下文 | 串口接收缓冲、帧解析、AT 事务 | 各自隔离阻塞点，队列容量随协议峰值实测 |
| 存储/OTA 上下文 | 串行化 Flash 写入和升级步骤 | 写入期间持有明确电源请求，支持断点/失败恢复 |

初始不引入一个可从任意模块发布任意事件的全局总线。先使用明确的调用和一个有界的产品事件队列；每增加事件，记录生产者、消费者、载荷上限、队列满时的处理方式和是否允许合并。周期工作用延时工作或专用采样上下文，按实际阻塞时间决定；不要复制旧工程的全局 20 ms `Poll` 循环。

## 6. 启动、故障与恢复

建议的启动依赖顺序：Zephyr 创建设备 → 日志/诊断可用 → 设备身份和配置恢复 → 电池/充电与按键可用 → 产品状态确定 → 按模式启动 IMU、BLE、GNSS、4G、UWB → 允许上报。实际每一阶段应可报告成功、受限或失败；关键数据损坏时使用版本化默认值和明确诊断。

外设错误由对应服务先分类并有限重试。IMU 连续采样失败时发布不可用状态并停止把旧数据当成实时运动信息；定位源失败可以降级，但应带有效性标志；4G 断线由网络服务负责重连；Flash 写入失败由存储或 OTA 服务返回明确状态。产品状态机决定是否进入 `FAULT`、继续受限运行或重启。看门狗只在关键执行单元确实推进时喂养。

## 7. 配置与电源归属

| 信息 | 存放位置 | 示例 |
|---|---|---|
| PCB 固定连接 | `boards/.../*.dts`、pinctrl、必要的 binding | IMU `&i2c1`、SCL P0.14、SDA P0.19、I²C 地址 0x6A |
| 编译能力与缓冲大小 | Kconfig、`prj.conf`、构建 profile | BLE、Sensor 驱动、日志级别、线程栈 |
| 产品默认策略 | `domain` 或相关服务的版本化默认配置 | 静止判定时间、休眠时间和重试门槛 |
| 可现场修改的参数 | `storage_service` 的版本化 schema | 定位间隔、服务器地址、报警阈值 |
| 运行状态 | 单一服务或 `product_app` 所有 | 当前模式、模组注册状态、最近有效定位 |

产品模式是策略层概念，不等同于 SoC 电源状态。`power_service` 根据产品模式协调外设和 Zephyr 电源管理；IMU 只执行被请求的采样档位。当前 PCB 的 LSM6DSO INT1/INT2 未连接，不能假定传感器中断可以单独唤醒整机；周期检测运动需要保留定时唤醒和采样能力，并实测待机电流。深睡唤醒源、4G/GNSS 电源顺序和外设掉电后的重新初始化，在对应电源切片明确。

## 8. 协议、存储与 OTA 的边界

GNSS 的 NMEA 解析、XRP/JT808 编解码放在纯逻辑 `lib/`，UART 和模组命令放在适配器中；定位服务只输出统一的定位结果。服务器会话、重传与离线补报由 `remote_service` 拥有，4G 适配器不解析产品协议。

OTA 的 BLE、UART/YMODEM 和 4G 实现仅接收固件块；`ota_service` 统一校验块顺序、写入、镜像状态、激活和错误处理，MCUboot 负责启动、确认与回滚。Flash 布局在引入 Bootloader 前依据真实镜像大小、内部/外部 Flash 与回滚要求定稿，并补充断电测试。`storage_service` 分开管理出厂身份、用户配置、离线记录和诊断数据，避免高频记录反复擦写配置区域。

## 9. 按切片落地与验收

| 切片 | 完成后可观察的结果 | 同时建立的边界 |
|---|---|---|
| S0：板级验证 | 当前 RTT、LED、按键、马达、IMU 基础读取可复现 | board DTS 与测试记录；已完成基本硬件验证 |
| S1：正式 IMU | 提供带时间戳的六轴样本及运动/静止事件；切换高低采样档 | IMU 适配器、服务、纯逻辑判定和回放测试 |
| S2：输入与 UI | 单击/长按等动作和产品反馈可独立测试 | 按键识别、UI 调度、产品事件队列 |
| S3：电源与配置 | 充电/电池、工作/待机切换、参数掉电恢复 | 电源/存储服务、状态机与配置 schema |
| S4：定位和联网 | GNSS 定位经 4G 完成一条服务器上报 | GNSS/4G 适配器、定位/网络/远程服务、协议库 |
| S5：其他产品能力 | BLE 配置、UWB、报警、工厂自检逐项达到旧行为 | 对应组件和端到端验收 |
| S6：升级与量产 | 多通道 OTA、回滚、功耗与故障恢复通过 | 分区、MCUboot、OTA 与生产测试 |

这个顺序允许按硬件风险调整，但每个切片都必须有可重复的板上现象或自动化测试。S1 的最小分层及板上回归已完成；下一步应从旧 `gt02_4g` 的真实构建目标提取 IMU 时序、阈值和输出，建立运动判定的纯逻辑测试，再测试工作/静止档位及故障路径。仅靠六轴读数正常，不能把产品需求 `IMU-001`、`IMU-002` 标记为完成。

## 10. 每次新增组件的检查点

1. 写明它拥有的状态、输入、输出、错误和时间单位。
2. 判断该状态是否已有其他组件所有者；发现重复所有权先改设计。
3. 确定运行上下文及最坏阻塞点，再设队列、栈和优先级。
4. 用正常、超时、断连/掉电或设备失效案例验证主要路径。
5. 更新需求状态、资源占用、功耗观察和对应验收记录。

只实现当前切片需要的接口。尚未开始的 BLE、UWB、OTA 等组件先按本文件规划边界，等有输入、输出和验收用例时再创建代码。
