# 4G最小服务与调用流程

这版只执行一次：上电 → 基础准备 → SIM查询 → 保存结果。先看清调用关系，再逐步增加注册、数据连接、重试和恢复。

## 先读这三处

| 入口 | 看什么 |
|---|---|
| [app/gt02_app.c](../../app/gt02_app.c) | 选择具体电源表和Lierda协议表，初始化AT后启动服务 |
| [service_worker](../../services/network/gt02_network_service.c) | 完整顺序流程集中在这个函数，没有额外状态机调度器 |
| [服务头文件](../../services/network/gt02_network_service.h) | 仅两个公共接口start、get_status，以及配置和状态 |

```text
应用装配：硬件init → AT初始化（启动唯一RX线程）→ service_start(config)
                                                       ↓
服务线程：power_on → 等待启动 → prepare → 等待事件 → query(SIM) → 等待事件
                                  ↓                     ↓
厂家/AT线程：                AT → ATE0             CPIN查询及解析
                                  ↓                     ↓
                             on_modem_event：复制完整事件到固定队列
                                                       ↓
服务线程：                              更新状态 → 打印结果 → 本轮结束
```

服务源码只包含公共能力契约，不知道Lierda命令ID、AT字符串、设备树或UART实例。
应用装配当前注入`gt02_modem_zephyr_power`和`gt02_lierda_ops`，更换实现时在装配处选择新表。

## 为什么只有两个服务接口

- `gt02_network_service_start(config)`：复制配置、绑定厂家事件回调、启动服务线程。绑定和启动放在一起，不额外拆一个只有转调用途的init。
- `gt02_network_service_get_status(out)`：在短锁内复制状态，不等待AT或直接访问厂家私有变量。启动前也可读取STOPPED。

配置包含两个长期操作表指针和`startup_delay_ms`。配置结构本身只需在start调用期间有效，表及实现必须长期有效。
当前装配的启动等待沿用NT26-KCN实板验证的2000 ms，不写死在服务内；硬件power_on自身仍负责原有板级时序。
start返回0只表示线程已启动，结果通过状态快照和日志观察。

## 线程和数据怎样分工

服务线程拥有流程与公开状态，AT线程拥有接收、事务和厂家解析。
`on_modem_event()`只用K_NO_WAIT复制事件，不保存借用指针、不在AT线程里上电或等待下一条命令。
`wait_result()`在服务线程等相应完成事件，再读取error；SIM结果必须等query完成之后才能使用。
首版队列只有两个事件槽位，队列溢出会锁存错误；每次等待最多10秒，避免异常情况下无限等待。
服务状态由短互斥锁保护，读取方得到独立快照；不使用volatile代替同步。

```text
STOPPED → POWERING_ON → PREPARING → QUERYING_SIM
                                      ├─ SIM_READY
                                      ├─ SIM_NOT_READY（包括PIN/PUK要求）
                                      └─ FAILED（任一步操作失败）
```

SIM_NOT_READY表示查询成功但卡未就绪，与查询失败分开；SIM_READY只表示SIM检查成功，不表示网络注册、PDP或TCP已就绪。
失败时保存负错误码，SIM设为UNKNOWN。服务不自动重试、解锁、断电或恢复。
等待保护到期只停止本轮，不取消尚未结束的底层请求；本轮结束后不支持再次start，必须重新启动设备。

## 默认构建与旧测试切换

```text
CONFIG_GT02_NETWORK_SERVICE=y
CONFIG_GT02_MODEM_AT_TEST=n
```

旧11条信息查询测试源码保留。需要返回该验证模式时，先将服务设为n，再将AT测试设为y，重新构建烧录。
Kconfig明确限制两个控制者互斥。CMake在任一模式启用时编译厂家适配，关闭测试不会把服务需要的厂家实现一起移除。
默认只发送AT、ATE0、AT+CPIN?，不再自动查询全部信息；未新增PDP/TCP/TTS操作。

预期日志如下，实际结果以实板回复为准：

```text
gt02_network: 4G service: power on
gt02_network: 4G service: prepare
gt02_lierda: AT handshake PASS
gt02_lierda: Echo off PASS
gt02_network: 4G service: query SIM
gt02_lierda: SIM state: READY (READY=1)
gt02_network: 4G service complete: SIM=2 (READY=1); network/TCP not tested
```

本版刻意保留顺序流程。重试、连续状态维护、上下电恢复、多连接和TTS待后续按需求增加；现有AT核心仍有故障后不可直接重新初始化的限制。

## 验证入口

[服务QEMU用例](../../tests/modem_at/src/service.c)默认链接真实服务、Lierda和AT核心，仅替换电源及UART。
在NCS工具链终端构建，使用工程外目录：

```powershell
west build --no-sysbuild -b qemu_cortex_m3 -d ../_verification/MyProject/modem_service tests/modem_at -- -DCONFIG_AT_TEST_SERVICE=y -DCONFIG_AT_TEST_SERVICE_CASE=0
west build -d ../_verification/MyProject/modem_service -t run
```

场景参数0..5依次为SIM就绪、需要PIN、准备ERROR、SIM超时、上电失败、立即回调的替代后端。
替代后端完全不启动AT，通过同一操作表在函数返回前交付事件，检查服务是否依赖具体厂家或错误的回调时序假设。
测试同时检查配置已复制、重复启动被拒绝、阶段顺序、只上电一次且没有多发命令。

本轮未自动烧录，仿真不能替代实板验证。IMU、Flash、LED、板级配置以及应用中已有的外设轮询注释保持原样。

## 本轮验证记录（2026-10-30）

- 默认最小服务构建通过，Flash 66,940 B、RAM 26,744 B。相对原全量查询默认构建66,704 B / 27,296 B，Flash增加236 B、RAM减少552 B；旧测试线程已由服务线程替换。
- 6组QEMU场景全部输出`PROJECT EXECUTION SUCCESSFUL`，覆盖上述成功、未就绪、准备失败、超时、上电失败及立即回调后端。
- 主构建确认CONFIG_GT02_NETWORK_SERVICE=y，旧AT测试控制者未启用；厂家源码独立于测试源文件选择。
- 关闭服务、开启旧AT测试的GT02构建通过，产物在工程外`../_verification/MyProject/legacy_information`，没有覆盖默认主固件。
- 服务测试日志在`../_verification/MyProject/modem_service/qemu_fault0.log`至`qemu_fault5.log`。服务源码不依赖Lierda头文件、AT命令或硬件驱动。
- 没有自动烧录；SIM_READY只说明本轮SIM检查成功，仍未实现网络注册、PDP、TCP、多连接和TTS流程。
