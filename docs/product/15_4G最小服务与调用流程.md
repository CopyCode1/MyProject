# 4G最小服务与调用流程

> 历史记录：2026-11-04已删除本页对应的`services/network/gt02_network_service.c/.h`、`tests/modem_at/src/service.c`、应用启动入口及服务专用Kconfig/CMake选择。
> 以下接口、流程、日志、测试命令及资源统计均描述删除前版本，不是当前可执行功能。相同服务文件路径现已重新实现为[驻网与数据就绪检测](16_4G驻网与数据就绪检测.md)，请以新文档和源码为准。

这版只执行一次：上电 → 等待启动事件 → 基础准备 → SIM查询 → CSQ信号检查 → LTE注册检查。全流程通过后`ready=true`，供后续TCP操作门控；不建立数据连接或TCP会话。

## 先读这三处

| 入口 | 看什么 |
|---|---|
| [app/gt02_app.c](../../app/gt02_app.c) | 选择具体电源表和Lierda协议表，初始化AT后启动服务 |
| `service_worker`（源码已删除） | 单一事件循环消费完成事件和定时期限，并推进状态 |
| `gt02_network_service.h`（已删除） | 仅两个公共接口start、get_status，以及配置和状态 |

```text
应用装配：硬件init → AT初始化（启动唯一RX线程）→ service_start(config)
                                                       ↓
服务线程：power_on → 等待STARTUP_READY → prepare → CPIN → CSQ → CEREG
                                  ↓                     ↓
厂家/AT线程：                AT → ATE0             CPIN / CSQ / CEREG解析
                                  ↓                     ↓
                             on_modem_event：复制完整事件到固定队列
                                                       ↓
服务线程：                       SIM就绪 → CSQ有效 → CEREG已注册 → ready → 本轮结束
```

服务源码只包含公共能力契约，不知道Lierda命令ID、AT字符串、设备树或UART实例。
应用装配当前注入`gt02_modem_zephyr_power`和`gt02_lierda_ops`，更换实现时在装配处选择新表。

## 为什么只有两个服务接口

- `gt02_network_service_start(config)`：复制配置、绑定厂家事件回调、启动服务线程。绑定和启动放在一起，不额外拆一个只有转调用途的init。
- `gt02_network_service_get_status(out)`：在短锁内复制状态，不等待AT或直接访问厂家私有变量。启动前也可读取STOPPED。

配置包含两个长期操作表指针和`startup_timeout_ms`。配置结构本身只需在start调用期间有效，表及实现必须长期有效。
当前装配将启动事件等待上限设为10000 ms，这是首版策略值，仍需实板确认；CPIN查询前等待2秒作为SIM稳定期限，由事件循环到期推进，不阻塞应用线程。
硬件power_on自身仍负责原有板级时序；超时从该接口返回后开始计算，之前到达的事件不会被清除。
start返回0只表示线程已启动，结果通过状态快照和日志观察。

## RDY怎样推进流程

Lierda厂家层把首次精确匹配的`RDY`转换为`GT02_MODEM_EVENT_STARTUP_READY`，不直接发AT，也不调用`finish_operation()`清除在途操作。
该事件表示可以尝试握手，命令通道是否正常仍由AT返回OK确认；它不表示已注册或TCP可用。
`ready_seen`只在本次开机去重，不支持重新上电复用；重复RDY保留日志但不再通知。

```text
start先注册厂家回调 → power_on（先建立RX再供电）
                             │ RDY可在接口返回前到达
                             ↓
厂家on_ready → 公共STARTUP_READY → on_modem_event按值入队
                             ↓
power_on返回 → 服务进入WAITING_READY → 取出事件 → prepare
```

没有启动事件时，服务以FAILED/-ETIMEDOUT结束，不发送AT、不自动探测、重试或断电。
迟到的RDY不能重新启动本轮。服务不能直接读取厂家私有`ready_seen`。

## 线程和数据怎样分工

服务线程拥有流程与公开状态，AT线程拥有接收、事务和厂家解析。
`on_modem_event()`只用K_NO_WAIT复制事件，不保存借用指针、不在AT线程里上电或等待下一条命令。
`on_modem_event()`只把完成事件复制入队；事件循环消费后按当前状态匹配结果、更新快照并提交下一项异步查询。
事件循环通过带期限的消息队列等待，CPIN前的2秒SIM稳定时间也是状态期限；没有同步等待AT结果的`wait_result()`或查询期间的`sleep`。
首版队列有两个事件槽位，队列溢出会锁存错误；RDY等待使用配置上限，每项AT操作最多等10秒。
重复RDY会被忽略且不延长期限；服务状态由短互斥锁保护，读取方得到独立快照。

```text
STOPPED → POWERING_ON → WAITING_READY → PREPARING → WAITING_SIM_SETTLE
    → QUERYING_SIM → SIM_READY → QUERYING_SIGNAL → QUERYING_REGISTRATION
                                                → REGISTERED (ready=true)
                                                └→ FAILED (ready=false)
```

CPIN非READY时流程失败；CSQ只接受RSSI 1..31，CEREG只接受stat 1/5。`ready`只在全部检查成功后置位，不代表PDP激活或TCP连接已建立。
`sim_ready`、`signal_ready`、`registered`分别反映已通过的检查，失败时保留已确认的条件；`ready`仅在三者都为true时置位。
服务不自动重试、解锁、断电或恢复。消息队列等待只挂起network服务线程，应用及其他Zephyr线程继续运行。
等待保护到期只停止本轮，不取消尚未结束的底层请求；本轮结束后不支持再次start，必须重新启动设备。

## 默认构建与旧测试切换

```text
CONFIG_GT02_NETWORK_SERVICE=y
CONFIG_GT02_MODEM_AT_TEST=n
```

旧11条信息查询测试源码保留。需要返回该验证模式时，先将服务设为n，再将AT测试设为y，重新构建烧录。
Kconfig明确限制两个控制者互斥。CMake在任一模式启用时编译厂家适配，关闭测试不会把服务需要的厂家实现一起移除。
默认依次发送AT、ATE0、AT+CPIN?、AT+CSQ、AT+CEREG?；未新增PDP/TCP/TTS操作。

## 验证入口

`tests/modem_at/src/service.c`（已删除的服务QEMU用例）默认链接真实服务、Lierda和AT核心，仅替换电源及UART。
在NCS工具链终端构建，使用工程外目录：

```powershell
west build --no-sysbuild -b qemu_cortex_m3 -d ../_verification/MyProject/modem_service tests/modem_at -- -DCONFIG_AT_TEST_SERVICE=y -DCONFIG_AT_TEST_SERVICE_CASE=0
west build -d ../_verification/MyProject/modem_service -t run
```

场景参数0..16覆盖完整启动成功、SIM PIN、AT准备失败、SIM超时、上电失败、同步回调后端、无RDY、延迟/重复RDY、CSQ为0/99/ERROR/超时、LTE未注册/无效正文/ERROR/超时。
真实AT/厂家路径覆盖启动通知在power_on返回前已到达、等待中到达、一直未到达、在握手/SIM期间重复到达。
替代后端完全不启动AT，通过同一操作表在函数返回前交付事件，检查服务是否依赖具体厂家或错误的回调时序假设。
测试同时检查配置已复制、重复启动被拒绝、阶段顺序、只上电一次且没有多发命令。

本轮未自动烧录，仿真不能替代实板验证。IMU、Flash、LED、板级配置以及应用中已有的外设轮询注释保持原样。

## SIM/信号/驻网启动门控

服务依次校验CPIN为READY、CSQ RSSI在1..31、CEREG stat为1或5；任一操作错误、正文非法或条件不满足都会进入FAILED并保持`ready=false`。成功后进入REGISTERED并置`ready=true`。当前TCP连接和数据收发能力仍未接入。
