本版接在[硬件适配](11_4G重建第一步_硬件适配.md)之上。实现固定及参数化短文本AT事务，尚未实现联网、TCP、提示符或二进制载荷。

后续已补齐[旧Lierda指令清单与基础查询](13_Lierda旧工程指令清单与接入.md)，并增加CEREG查询；当前命令表为22项，其中QIACT查询已提供结构化数据上下文结果，APN/激活等仍为预留。
旧自动上电测试可顺序执行原11条固定命令；默认入口为[驻网与数据就绪检测](16_4G驻网与数据就绪检测.md)，下面测试流程及早期构建数据按对应迭代阅读。

2026-11-05调整：保留SUCCESS/FAILED/TIMEOUT三种结果；明确错误回复继续调度，超时转隔离等待而非永久停止。
隔离期收到旧结束行、当前批次处理完且无残行后恢复；隔离预算默认5000ms，到期转FAULTED并通知外部。

## 初始化和提交接口怎么使用

```c
static const struct gt02_at_config config = {
    .profile = &gt02_lierda_at_profile,
    .io = &gt02_modem_zephyr_io,
};

gt02_at_init(&config);
gt02_at_submit(LIERDA_CMD_CSQ);
```

参数化命令由厂家适配检查参数、构造文本，再调用`gt02_at_submit_text(id, text)`。
固定项继续用submit；参数化项用普通submit返回-EINVAL，固定项用submit_text同样拒绝。
文本须为最多128字节的可打印ASCII，以注册命令名紧跟等号开头，等号后至少一个字符。
成功入队前已复制完整文本，调用者可复用或释放局部构造缓存；不复制user_data。
LGPIO内部辅助声明集中在[厂家头文件](../../adapters/modem/gt02_modem_lierda.h)，服务层不依赖它们。

init一次绑定协议表和I/O操作并启动AT线程，不上电、不发命令；先准备硬件，再由测试或未来生命周期服务组织上电。
config本身只需在初始化期间有效，内部保存的profile、io及其成员和回调参数必须长期有效，运行中不更换。
submit返回0只表示入队成功。非法标识、队列满、未初始化或已故障的请求立即返回错误，不产生回调。
已接收请求按FIFO处理，每次回调都使用对应表项的user_data；当前没有逐请求编号，重复标识仍是独立队列项。

命令表注册发送内容、正文前缀、最终回调、参数、超时和正文必需标记。核心统一加CRLF。
`reserved=true`仅登记待接入项；submit返回-ENOTSUP，不发送、不回调，允许该项没有最终回调。
正文前缀NULL不收集，非空前缀按原规则匹配，空字符串则在已注册URC之后兜底收集ATI等无前缀正文。
URC表注册内容、整行/前缀匹配方式、回调和参数。表及参数不得引用已退出函数的局部对象。
第一版拒绝归属重叠的URC/非空正文前缀规则；不能简单把两个同前缀规则放进表里期待自动区分查询与主动上报。
空字符串是显式的低优先级兜底规则，已注册URC先处理；未知URC仍可能混入该类正文。

## 能力接口如何注入

应用装配层集中选择协议配置和硬件实现，只有装配及具体适配器需要知道Zephyr硬件导出的操作表名称。
接口契约本身没有线程或中转函数，不增加运行时服务层。

```text
app/gt02_app.c装配
  ├─ modem_at_config.profile = Lierda命令/URC表
  ├─ modem_at_config.io = gt02_modem_zephyr_io
  │       → AT核心保存transport → transport->read()/write()
  └─ gt02_modem_zephyr_power
          → 准备硬件，并作为参数交给临时控制入口
          → power_ops->power_on()
```

| 接口组 | 使用者 | 提供的能力 |
|---|---|---|
| `gt02_at_io_ops` | AT事务核心 | read、write，没有电源控制权限 |
| `gt02_modem_power_ops` | 装配/生命周期调用者 | init、power_on、power_off，没有原始字节收发 |

Zephyr适配器只导出两份只读绑定对象，内部仍执行原五个硬件函数，没有改动上下电时序、错误码及锁策略。
AT核心不再包含`gt02_modem_zephyr.h`，也不引用`gt02_modem_hw_read/write`。
QEMU测试注入不同名称的静态fake_read/fake_write，不依赖链接时替换同名硬件函数。

当前周期检测服务使用注入的电源/厂家表组织上电和持续检查；新增AT故障通知与一次受控重启。临时验证入口保留为互斥模式。
原始硬件循环测试仍可直接验证实际硬件函数，不能与AT消费者同时运行。
操作表启动时固定；新增session_rearm只负责故障后的会话重新开放，不提供正常关机、运行时热切换或多模组实例。
当前接口继续使用Zephyr的k_timeout_t，支持在同一RTOS下换硬件，不等于已经实现跨RTOS移植。

## 一个命令只有一次最终回调

| 收到的内容 | 行为 |
|---|---|
| `+CSQ: 18,0` | 保存匹配正文，尚不修改业务结果 |
| 随后收到`OK` | 回调SUCCESS，交付正文；回调检查格式后更新信号 |
| 随后收到`ERROR`或CME/CMS错误 | 回调FAILED，response=NULL、length=0，不交付半截结果 |
| 仅收到OK，缺少要求的CSQ正文 | 回调FAILED |
| 到截止时间仍未结束 | 回调TIMEOUT，取消待发请求并隔离旧回复；旧结束行及残留输入处理完后恢复调度 |
| `RDY` | 即时URC回调，不结束当前命令 |

AT层SUCCESS只证明本次协议完成，不能替代正文格式和数值范围校验。Lierda回调允许RSSI为0..31或99，BER为0..7或99；99表示未知。
解析失败通过负错误码交付，不把半截正文当成有效信号。厂家不再另存无人读取的信号缓存；公开结果由服务的整轮快照统一维护。

所有回调在AT线程执行。命令最终回调在SDK解析处理返回后调用，不持请求队列锁；URC回调由SDK处理过程中调用。
回调不能阻塞等待其他AT请求，但可以非阻塞submit。接收指针仅在回调期间有效，需要长期保存时复制字段。

## 缓存、调度和失败边界

当前主循环只保留三个按执行顺序排列的步骤：

```text
at_worker
  1. 检查本轮开始前的超时或已锁存发送错误
  2. receive_input：等待一批UART输入并送入解析器
  3. advance_transaction：处理本轮结果、完成回调或调度下一条请求
```

`receive_input()`内部处理本轮字节数，将硬件读错误登记到`pending_error`，不再返回字节数或向Worker传递接收历史参数。
read期间跨过事务期限时，先通知超时再解析本批旧输入，不丢弃其中的结束行。
`advance_transaction()`不再返回stopped标志，而是根据正常、隔离、故障状态推进；明确ERROR只结束当前请求。
超时进入CORE_DRAINING，继续RX/URC，收到旧最终结果且当前批次结束、没有残行时恢复CORE_READY。
隔离到期进入CORE_FAULTED，由Worker清理事务和SDK残留、通知一次故障，继续接收URC；明确重建会话后才允许rearm。
未确认旧事务结束时submit返回-EAGAIN，不通过静默计时或清缓存强行放行；传输/解析完整性故障仍返回-EPIPE。
这两个内部步骤不新增公共接口、线程或独立业务状态，原有命令/URC分发与最终回调仍在原函数中。

- 一个AT线程，优先级6、栈3072字节；4个待执行请求，另外允许1个在途事务。
- 队列4个文本槽位与1份独立在途存储，每份最多128字节命令另加NUL；出队复制后才复用原槽位，不使用动态内存。
- 回显匹配使用本次完整文本，参数化表项的命令名不参与替代参数或过滤完整回显。
- 一份512字节正文缓存，另留NUL空间，不给每个命令分配response数组。多行正文以换行分隔。
- 单行上限256字节。SDK使用4个512字节固定net_buf块，不使用通用堆；硬件原始RX环仍为2048字节。
- SDK只接收预先检查过行长的小片段，防止截断匹配和固定池耗尽。启动二进制内容作为未知行转义记录，不当作AT正文。
- 保留CR/LF文本日志，不再由旧测试线程抢读串口。输入停在未结束的半行时，不会直接把它拼入新事务；首版拒绝在这种空闲间隙启动新请求并报告失步。
- 空闲接收最长等待20 ms后检查请求。超时从开始发送计算，不包含排队；实际硬件write没有超时，因此无法保证异常硬件下的严格总耗时。
- 明确ERROR结束当前事务后继续队列，不向上额外展开具体错误码，保持SUCCESS/FAILED/TIMEOUT三种结果。
- 超时只通知当前请求一次TIMEOUT，未发送请求各通知FAILED；提交入口暂时返回-EAGAIN，业务重试由上层调度。
- 旧OK/ERROR/CME/CMS结束行只解除超时隔离，不再次回调；同批数据及未结束残行排空后才恢复提交。
- 一直没有旧结束行时保持隔离，不能保证模组完全不回复时自动恢复；这是单命令文本模式策略，不能识别非标准异步同名结束行。
- 部分发送、硬件流错误或在途输入超限仍进入CORE_FAULTED，后续提交-EPIPE；不自动重发、切电或复位模组。

## 自动化验证入口

[QEMU测试](../../tests/modem_at/src/main.c)链接真实AT核心及SDK解析器，显式注入假I/O；不链接具体硬件适配器，不会驱动真实GPIO、电源或Flash。
在已加载NCS工具链的终端执行，QEMU路径按安装位置设置：

```powershell
$env:QEMU_BIN_PATH = 'C:/Users/Administrator/zephyr-sdk-1.0.1/hosttools/qemu'
west build --no-sysbuild -b qemu_cortex_m3 -d ../_verification/MyProject/modem_at tests/modem_at -- -DCONFIG_AT_TEST_FAULT_CASE=0
west build -d ../_verification/MyProject/modem_at -t run
```

主固件始终使用`build_ncs_341`，应用源目录为本工程根目录；QEMU应用源目录为`tests/modem_at`，两者不能复用构建目录。
测试产物放在工程外的`../_verification/MyProject/`，避免VS Code把测试构建误当成主固件配置。
此前根目录的`build_at_tests`等临时构建已归档到该目录的`archives/`，保留验证日志；移动后的CMake缓存仅作记录，不用于原地继续构建。

故障参数0..4分别表示超时、部分发送、单行超限、正文累计超限和硬件接收错误。每次开机只注入一种终止性故障，因为生产核心没有reset接口。
每种配置都先检查单字节拆包、多行粘包、回显、URC穿插、正文后ERROR、缺失正文、扩展ERROR、FIFO顺序和回调内再提交；最后检查队列满拒绝、故障取消恰好一次及迟到回复不会完成新命令。
参数化扩展额外覆盖128/129字节边界、错误提交模式/命令名、CRLF注入、调用者改写缓冲、在途与四条排队请求隔离、厂家GPIO构造及固定/参数化混合取消。
