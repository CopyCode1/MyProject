# GT02 简洁实现与可读性

## 目标与适用方式

落实用户的开发偏好：代码容易理解，必要边界清楚，复杂度与当前需求相称。
来源为用户的 [MCU编程规范讨论](https://chatgpt.com/share/6ae3fd18-70ac-83ee-a070-07f4a31fe175)
及其在本工程中确认的总结；该讨论表达设计偏好，不是协议或硬件事实依据。

实现、评审、重构时按当前问题选用下列规则，不强制输出完整检查表。
只修改任务涉及的代码；启用本技能不意味着需要重构整个工程。

## 用读者的问题组织代码

代码应让具有嵌入式经验、未参与项目的工程师，在理解局部功能时无需先掌握整个系统。
文件入口、类型、函数顺序和少量必要注释，应帮助他回答：

- 模块为何存在，管理哪些资源和状态，由谁拥有和修改？
- 收到哪些输入，什么条件改变行为，结果交付给谁？
- 出错后如何结束、重试或停止，资源何时释放？
- 修改某项功能时，应定位到哪个状态分支或独立职责？

对状态处理函数，优先让读者直接找到“当前状态 → 可接受事件 → 动作 → 下一状态 → 异常出口”。
少量状态可用集中switch和直接分支，不强制所有模块套同一状态机框架，不为每个赋值创建转调函数。
状态由一个逻辑所有者在受控路径修改，不等于所有赋值必须经过同一个set_state函数。

把复杂性限制在需要理解它的地方；验收目标是正确理解代码比误解代码更容易，不以行数、函数数量或设计模式数量衡量优劣。

## 函数：让阅读顺序接近执行顺序

- 主函数体现主要流程，辅助函数封装具有独立工程意义的细节；阅读主流程时应能看清步骤及错误去向，减少同时需要记住的状态和关系。
- 优先清楚呈现参数检查、主要步骤、错误处理和结果输出，避免复杂表达式及不必要的深层嵌套。
- 能独立结束的非法输入和失败路径可提前返回；持锁、持有资源或硬件已改变时，仍需经过正确的收尾路径。
- 函数名表达操作，变量名表达含义；时间、容量、物理量标明单位。关键协议偏移、长度和时序参数用少量有意义的常量或注释解释，不要求每个数字都变成宏。
- 让调用者明确阻塞、输出有效性、状态副作用及失败结果。检查实际实现和调用方，不凭函数名推测保证。
- 不设置统一的函数行数、参数数量或嵌套层数硬指标；以理解主流程、边界和状态的成本判断是否需要调整。

## 拆分与抽象：先说明收益

| 当前情况 | 优先选择 |
|---|---|
| 短小、连续、仅使用一次的步骤（如地址解析中的几次直接移位） | 留在主流程中，按自然顺序组织，不为形式增加转调 |
| 重复逻辑，或可以独立理解和验证的复杂细节 | 提取内部辅助函数 |
| 硬件、具体模组协议与业务策略由不同原因改变 | 保留相应模块边界，避免上层直接依赖具体实现 |
| 包装仅增加转调，没有提供稳定契约、差异隔离或测试替换点 | 不新增；评审时说明收益是否足够 |

- 不为统一形式给每个步骤创建函数、结构体、回调表、线程或队列；有明确调度、生命周期、变体或所有权需求时再增加。
- 不因当前只有一个实现就删除已有的有效隔离；也不为了缩短函数将业务、协议与GPIO重新耦合。
- 使用简单的条件判断或switch足以表达少量分支时，先保持直观实现。分支明显增多或具有独立复杂度后再考虑拆分或表驱动。
- 对外只公开当前调用者需要的操作，其余尽量保持私有。现阶段4G硬件层以初始化、上电、下电、读、写五个入口为起点；该数量不推广为其他模块的固定上限。
- 参数表达调用者提供的真实变化；模块独占的内部记录可以收回所属上下文。保留能说明对象归属、错误原因和数据边界的参数，不为减少参数把依赖全部变成全局变量。

## 简洁不能省略的运行约束

- 二进制数据使用指针加实际长度，区分容量与已接收长度；访问字段前确认边界，涉及长度计算时检查溢出及类型转换。
- 对解析或计算函数，先完成本次调用所需的全部输入校验，再提交输出；需要中间计算时保存在局部变量，失败不交付半成品，不为此机械新增结构体或包装函数。若既有接口明确允许部分写入，应按授权范围保留或显式调整契约。
- 函数输出提交与异步业务的过程状态分开：上电中、查询中等已发生的阶段应及时发布；每个完成结果须通过该阶段校验后再提交，不能要求整个业务成功后才更新所有状态。
- 约定缓冲区和状态由谁拥有、何时可复用；共享状态使用匹配上下文的同步方式，不能用volatile代替同步。
- 中断只承担必要且有界的工作；阻塞等待、复杂解析和日志放在允许的执行上下文中。必要的锁、队列和会话检查不能因追求代码短而直接删除。
- 错误保留来源，明确失败后的硬件、缓存及状态；清理失败与原始失败分开记录。由负责策略的模块决定重试或重启，避免各层自行重复恢复。
- 接口完成、模组就绪、联网成功和对端确认是不同结果，按照实际完成条件报告。
- 异步操作明确谁负责最终完成及超时；避免为同一操作在每层设置互相独立的计时器。只有真实业务需要且取消/迟到结果语义明确时，才引入不同层级的业务期限。
- 将“下次动作时刻”“启动截止时刻”“结果有效期”按用途表达；历史观测和临时解析数据生命周期不同，不能因统一清理而误重置。
- 优化应有时序、内存、调用频率或测量依据；同时考虑RAM、Flash、栈、复制开销及最坏执行时间，保留真实硬件要求的操作顺序。

## 重构：先确认哪些行为要保留

先核对调用者及现有测试，识别本次相关的行为约定：返回值、消息优先级、重复消息策略、长度兼容性、失败时输出、超时、并发和硬件时序。

- 整理结构时保留已约定行为；发现缺陷，区分等价重构与行为修正，在当前授权范围内处理并明确说明差异。
- 不将更严格的长度拒绝、有效标记重置或错误码变化隐瞒为单纯排版调整。
- 按风险验证正常路径及受影响的边界/失败路径；协议或硬件行为变化需相应证据，不能用编译通过替代。
- 写明验证限度：模拟类型测试不等于真实工程构建，构建成功不等于实板、协议或长期稳定性验收。

## 协作与交付

- 说明文字和注释使用中文，保留代码标识符。编写或修改C函数及头文件时，配合 [中文函数与接口注释规范](../gt02-code-comments/SKILL.md)，不在本技能重复完整注释格式。
- 遵循工程现有Zephyr风格；借鉴MISRA C、CERT C等安全规则时核对适用内容，不将本技能声称为完整标准合规要求。
- 方案有实际取舍时，简要比较保留直接实现与增加抽象的收益和成本；不为每个小改动展开架构论证。
- 交付说明实际改动、保留或调整的行为、验证结果及未确认事实。让工程师能够追溯决定，不以目录数量、函数数量或生成代码量衡量质量。
