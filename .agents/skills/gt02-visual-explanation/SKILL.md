# GT02 中文讲解与图表

## 讲解原则

- 先回答用户当前问题，再给必要的依据与解释；保持老师式、循序渐进的中文讲解，不一次铺开整个产品架构。
- 图表用于降低理解成本，不用于装饰。简单事实、单行配置、单步操作直接用文字或短代码说明。
- 判断图表是否有用：它是否比一小段文字更清楚地表达层级、多个对象的映射、交互顺序、状态变化或数据归属？没有明显收益就不画。
- 优先使用最小且足够的图表。图旁说明读图要点，不再用长篇文字重复每个节点。

## 选择合适的表达

| 要解释的关系 | 优先表达 |
|---|---|
| 模块层级、依赖、职责边界 | 简洁架构图；需要逐项区分职责时用表格 |
| API到驱动的调用链、发送与接收路径 | 流程图或带方向的文本调用链 |
| 命令、响应、URC、多线程协作的先后 | 时序图；标出执行者、等待和通知 |
| 启动、联网、断线重连和故障恢复 | 状态图；标出触发事件、失败及超时出口 |
| 多连接缓存、共享UART、队列与消费者 | 数据流图；区分独立与共享资源 |
| 文件作用、配置归属、方案取舍 | 紧凑表格 |
| 分阶段落地或可观察事件的时间顺序 | 简短步骤；复杂依赖才使用时间线或流程图 |

这些是选择建议，不要求每次回答同时包含多种图。用户明确要求某种形式时优先满足该要求。

## 绘图与事实边界

- 默认使用Markdown表格或围栏代码块中的文本图，保证聊天和普通Markdown预览都能阅读。
- 用户要求Mermaid或已确认阅读环境支持时，可使用Mermaid；不要为讲解安装插件或调用图像生成工具。
- 图中以中文解释角色，保留源码中的API、文件名和标识符以便定位。
- 明确箭头代表请求、函数调用、字节流还是结果事件；必要时区分正向请求和反向通知。
- 讨论现有实现时，依据实际源码；未核对的部分标为待确认。方案图明确标注“设计方案”，不能画成已经实现或验证的事实。
- 不混淆软件层与线程、TCP连接与UART、命令接受与连接成功、入队成功与模组发送结果及平台应答。
- 状态图按问题需要表达失败和超时；并发图按问题需要表达谁等待、谁继续接收、谁拥有状态或缓冲。
- 简化图形时保留当前问题的关键约束，不为易懂而假装多个共享资源彼此独立或操作可任意并行。

## 对话与设计文档

- 普通问答只在回答中给必要图表，不自动改写工程文档或源文件。
- 用户要求保存说明，或已授权的实现导致设计发生变化时，把有维护价值的图表和说明同步到对应设计文档，避免另存一份重复设计。
- 新建项目说明文档使用中文文件名；`SKILL.md`、`agents/openai.yaml`及代码标识符保留工具或工程约定的名称。
- 只调整讲解方式，不替用户决定硬件参数、产品策略或额外实现范围。与产品工程技能同时使用时，本技能补充表达方式，不替代架构和验证要求。
